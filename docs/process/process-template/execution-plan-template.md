# [Loop Name] Execution Plan

## Назначение

Этот документ задает непрерывный execution loop для `[loop scope]`.

Он одновременно является:

- полным task-driven планом работ;
- управляющим execution loop без промежуточной остановки;
- системой phase gates;
- критерием перехода между фазами;
- критерием финального `done` для данного цикла.

Этот документ не заменяет system docs, domain requirements и
другие active process docs, если они существуют.

## Область действия

Документ обязателен для всех работ, которые одновременно:

- относятся к `[domain / slice / release scope]`;
- требуют непрерывного продвижения по задачам, а не разового изменения;
- используют единый набор statuses, checks и transition gates;
- должны фиксировать следующее действие сразу после завершения текущего.

## Режим непрерывной разработки

Цикл должен вестись как непрерывная разработка до полного завершения scope.

Допустимы только следующие точки остановки:

- `done`: все фазы, задачи, проверки, gates и финальный acceptance завершены;
- `blocked`: существует реальный blocker, который:
  не снимается локальным инженерным действием;
  зафиксирован как решение в decision log;
  имеет явно описанное влияние на дальнейший ход работ.

Промежуточный прогресс не считается допустимой точкой остановки.

После завершения любой задачи исполнитель обязан:

1. Обновить ее статус.
2. Проверить gate текущей фазы.
3. Если gate не пройден, перейти к следующей допустимой задаче той же фазы.
4. Если gate пройден, немедленно перейти к следующей фазе или задаче.
5. Не завершать работу отчетом, пока в цикле есть хотя бы одна задача со
   статусом `pending` или `in_progress`, кроме случая реального `blocked`.

## Статусы задач

Каждая задача в этом плане может находиться только в одном статусе:

- `pending`
- `in_progress`
- `done`
- `blocked`

Статус `done` допустим только после прохождения всех обязательных проверок для
задачи и ее фазы.

## Общий алгоритм исполнения

На каждом цикле исполнения нужно строго делать следующее:

1. Открыть этот документ.
2. Найти первую задачу со статусом `in_progress`.
3. Если такой задачи нет, найти первую задачу со статусом `pending`, для
   которой выполнены все зависимости и prerequisites.
4. Перевести ее в `in_progress`.
5. Реализовать задачу полностью в рамках ее определения.
6. Выполнить обязательные проверки для задачи.
7. Если проверки не пройдены, продолжать исправления в рамках той же задачи.
8. Если проверки пройдены, перевести задачу в `done`.
9. Проверить transition gate текущей фазы.
10. Если фаза не закрыта, немедленно перейти к следующей задаче этой фазы.
11. Если фаза закрыта, немедленно перейти к следующей фазе.
12. Повторять цикл, пока не наступит `done` или реальный `blocked`.

## Общие контрольные правила

Во всех фазах обязательны следующие правила:

- нельзя вводить fake foundation в critical planes;
- нельзя использовать prototype-first или skeleton-first path;
- нельзя откладывать обязательные свойства цикла "на потом";
- нельзя создавать второй competing owner для domain truth;
- нельзя переходить к следующей фазе без прохождения transition gate текущей;
- нельзя считать цикл завершенным без тестов, diagnostics visibility и
  operator-visible результата там, где это обязательно по scope.

## Блокеры и решения

Если цикл допускает blocker scenarios, они обязаны обрабатываться по следующим
правилам:

- blocker сначала классифицируется;
- затем выбирается допустимый compensating path или formal decision;
- решение фиксируется в decision log до продолжения значимого следующего шага;
- blocker не должен маскировать архитектурный drift, fake foundation или
  несоответствие source of truth.

Если цикл не требует отдельного decision log, этот раздел должен быть
переопределен явным текстом.

## Точки контроля качества

Контроль должен происходить внутри цикла, а не только в конце:

### Code Control

- сверка с system docs и domain docs;
- запрет на drift относительно development contract;
- проверка ownership boundaries и package/file shape, если цикл затрагивает
  структуру кода.

### Dependency Control

- проверка роли новой зависимости;
- проверка support posture и известных уязвимостей;
- запрет на silent dependency substitution в critical planes.

### Runtime Control

- наличие explainable diagnostics для нового runtime behavior;
- отсутствие fake runtime truth;
- operator-visible состояние для degraded и failed путей, если цикл их
  затрагивает.

### Test Control

- наличие целевых unit tests;
- наличие integration/e2e coverage там, где это требуется scope;
- явная проверка failure/degraded paths, а не только happy path.

## Финальный acceptance gate

Цикл может перейти в итоговый `done` только если одновременно выполнены все
условия:

- все фазы и задачи находятся в допустимом terminal state;
- нет незакрытых blocker decisions, требующих follow-up внутри этого же цикла;
- documentation, code и tests синхронизированы;
- source-of-truth docs не противоречат финальному результату;
- scope цикла не оставил обязательные свойства в deferred состоянии.
