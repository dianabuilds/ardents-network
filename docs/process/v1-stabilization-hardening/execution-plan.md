# V1 Stabilization And Hardening Execution Plan

## Purpose

This document governs the continuous development loop that moves the current
root Ardents implementation from technical alpha to a release-candidate `v1`.

The loop covers stabilization, security remediation, privacy, network
participation, workload execution, hosted services, distributed data behavior,
operator experience, QA hardening, and release evidence.

It does not reopen the canonical network decision: Ardents `v1` remains
Waku-backed.

## Target Outcome

The loop is complete only when a supported Ardents node can be installed,
configured, started, joined to a real multi-node Waku network, observed,
restarted, and safely operated while:

- identity and runtime truth survive restart;
- relay, store, filter, and lightpush roles are represented truthfully;
- private product semantics do not enter Waku as readable topics or payloads;
- workloads run through a product-grade isolation boundary;
- hosted services are published only from observed readiness and reachability;
- encrypted data can be retained, replicated, fetched, re-served, and repaired;
- policy and security decisions change runtime behavior visibly;
- tests, diagnostics, security scans, release artifacts, and operator docs agree
  with the runtime.

## Scope And Ownership

Owning process area: repository-wide `v1` release stabilization.

Owning product domains remain unchanged:

- `Node Runtime`: node lifecycle, continuity, and node-level readiness;
- `Identity`: stable identity and subject authenticity;
- `Network Foundation / Messaging`: Waku participation and messaging truth;
- `Discovery`: remote knowledge and trust-aware resolution;
- `Publication`: local presence and service publication outcome;
- `Workload Control`: execution lifecycle and observed workload truth;
- `Hosted Services`: service specification, readiness, and exposure eligibility;
- `Data Substrate`: content, retention, transfer, availability, and repair;
- `Policy`: behavior-changing rules;
- `Diagnostics`: operator-visible explanations.

Runtime assembly, local control surface, Proto/Connect, HTTP, CLI, test runners,
and deployment packaging remain non-domain layers.

## Status Model And Execution Algorithm

Allowed task statuses:

- `pending`
- `in_progress`
- `done`
- `blocked`

Execution algorithm:

1. Open this document and the decision log.
2. Continue the first `in_progress` task.
3. If none exists, choose the first `pending` task whose dependencies are done.
4. Mark only that task `in_progress`.
5. Read the required project skill and source-of-truth documents.
6. Implement the whole task and its required observability/test surface.
7. Run the task checks and record evidence paths in its `Evidence` field.
8. Mark the task `done` only after all checks pass.
9. Evaluate the phase transition gate.
10. Continue immediately with the next task or phase.
11. Use `blocked` only when local engineering alternatives are exhausted and a
    decision-log entry records the external dependency and impact.

No phase may begin before the previous transition gate passes. No final response
is allowed while the active phase contains an admissible `pending` or
`in_progress` code task.

## Universal Controls

Every implementation task must satisfy all applicable controls:

- architecture and domain ownership are explicit;
- Waku remains the real network carrier;
- no critical path is replaced by a fake or metadata-only substitute;
- new or upgraded foundational dependencies pass dependency safety review;
- handwritten Go file/function limits pass `ardents-code-size-guard`;
- security-sensitive paths pass `ardents-runtime-security-guard`;
- success and failure/degraded paths are observable;
- unit tests live with domain code;
- integration/E2E tests use formal `testkit.Spec` metadata and scenario docs;
- canonical runners, not ad-hoc competing runners, produce test evidence;
- logs, diagnostics, reports, and API output do not expose secrets or capability
  material.

## Phase Dependency Map

```text
Phase 0 baseline trust
  -> Phase 1 dependency and boundary security
    -> Phase 2 network privacy
      -> Phase 3 participation and reachability
        -> Phase 4 workload and hosted-service runtime truth
          -> Phase 5 distributed data availability
            -> Phase 6 policy, operations, and product usability
              -> Phase 7 adversarial QA and release acceptance
```

Testing is not deferred to Phase 7. Each task must land its own tests; Phase 7
performs system-level pressure and final acceptance.

## Final Acceptance Gate

The loop may enter terminal `done` only when all conditions hold at once:

- every task is `done` and no active decision requires follow-up inside this
  loop;
- all canonical commands and supported-platform jobs pass from a clean checkout;
- no remediable reachable high/critical vulnerability remains;
- every accepted residual risk has complete containment, detection, owner, and
  upgrade trigger documentation;
- Waku is the actual carrier and relay/store/filter/lightpush truth is proven;
- private product semantics are absent from tested readable carrier topics and
  payloads;
- workload isolation, resource limits, recovery, and failure diagnostics work;
- service publication depends on current observed readiness and reachability;
- encrypted data replication, fetch, re-serving, repair, quota, and terminal loss
  behavior are real and observable;
- identity, runtime, diagnostics, pending operations, and required state survive
  restart according to their contracts;
- local control, configuration, deployment, backup/restore, upgrades, and release
  artifacts are usable by an operator from documentation alone;
- mutation, chaos, performance, multi-host, and soak evidence contain no
  unresolved blocker;
- source-of-truth docs, domain docs, process docs, code, tests, security register,
  and runtime output agree;
- no mandatory property touched by the loop remains deferred as “later”.

If any condition fails, the active task remains `in_progress` or returns to the
appropriate earlier phase. Intermediate progress is not terminal completion.
