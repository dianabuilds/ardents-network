# Agent execution and handoff

This engineering workflow applies to the authorized closed text-Service work.
It changes neither the product contract nor the repository authority order.
GitHub Issues in the C0 milestone own delivery state; this file is not a ledger.

## Delegated project-wide domain transition

The Product Owner delegated the entire DDD transition on 2026-10-04, including
domain design, visible implementation threads, verification and delivery into
`dev`. The orchestrator carries this program to completion. A bounded issue,
implementation slice, thread turn or context compaction does not end the
assignment. Do not ask the Product Owner to select the next slice or repeat
permission already granted for this program. GitHub records the concrete
selection and execution status; this section records the execution contract.

Repeat the following cycle until every maintained project scenario is carried
by the completed domain model:

1. **Design and verify the domain before assignment.** Inspect current product
   and technical contracts, code and real consumers. Define its question,
   language, rules, aggregates and distinct consistency owners, state, resources,
   termination, exclusions, dependencies and narrow inter-domain contracts.
   Inventory responsibilities in both directions: recover its rules from other
   owners and return unrelated rules to their proper owners. Identify existing
   defects, independent behavioral oracles, durable/byte compatibility and the
   complete regression and release acceptance boundary. Keep technical mechanisms
   distinct from domain authority; do not manufacture aggregates for simple
   adapters. Resolve design from current authoritative evidence rather than
   repeatedly interviewing or requesting routine decisions from the Product Owner.
2. **Assign a goal to a visible executor.** For each next domain, create an
   ordinary visible Codex thread and give its implementer the verified design,
   source identity, actual consumers, all acceptance parameters, required profiles
   and a concrete goal: implemented domain behavior, full regression with the new
   domains, scoped commits and integration into `dev`. Continue the existing
   authorized executor for an active domain. Slices are manageable steps toward
   its release, not permission checkpoints or substitute domain completion.
   Record each active issue in the C0 ledger within the existing WIP count.
3. **Implement, diagnose and repair.** The executor owns implementation and
   tests; the orchestrator owns design, domain-map reconciliation and review of
   completed results. Maintain one implementation owner for the sequential
   dependency chain in its existing checkout. Internal agents may own bounded
   subtasks with disjoint responsibilities; the overall goal, decisions, progress
   and acceptance stay visible. Preserve unrelated work and the existing index.
4. **Run complete regression in the new-domain environment.** Exercise real
   product consumers with genuine new authority and durable owners, successful
   and causal refusal paths, concurrency, persistence and joined resource
   termination. Cover every affected new domain, both selected Carriers where
   applicable, and the required quick/full gates on the final source. A moved
   source file, old-runtime bridge, fake successful neighbor or prior-revision
   pass cannot satisfy integration. Repair discovered defects at their owners;
   retain failures and source-matched evidence without weakening gates.
5. **Deliver and verify `dev` integration.** The executor commits the coherent
   verified domain changes, preserves unrelated work, merges into `dev` when a
   separate branch was used, and pushes the resulting `dev` revision. The Product
   Owner has already authorized commits, pushes, merges into `dev`, and creation
   and publication of tasks/results in GitHub. Neither agent requests another
   approval for those actions. Keep normal hooks and required checks enabled;
   confirm the integrated source and remote revision. The orchestrator checks
   boundaries and evidence, reconciles the complete domain map and owning
   documents, and returns precise defects to the same executor when necessary.
6. **Continue to the next domain.** After the domain's complete release boundary
   and `dev` integration are verified, the orchestrator designs and verifies the
   dependency-ready next domain, then repeats this cycle without waiting for a
   Product Owner prompt. Do not close the program while any maintained scenario,
   domain responsibility, real consumer or required release proof is missing.

Do not summon the Product Owner or stop the implementation thread because a
slice finished, a test failed, an environment needs repair, a tool is inconvenient,
or a summary lost the assignment. Diagnose, fix and continue, repeating the
engineering cycle as many times as needed. A defect or an authority refusal may
require safely cancelling and joining that physical operation; it does not end
the visible development assignment. Repeated engineering attempts do not grant
new protocol retries, refunds, redraws, deadlines or relaxed safety bounds.
Record genuine unresolved evidence honestly and continue useful work within
the accepted product and security contracts; do not invent a successful result.

After every compaction or handoff, recover this program mandate, current domain,
visible executor, design, source, evidence and next result. Read the Route
migration contract in full whenever Route is involved and preserve its isolation
and acceptance rules. The Product Owner instructed the orchestrator not to edit
`AGENTS.md`; maintain this execution owner and the domain owners instead.

## Resume from evidence

1. Read the active task's compact handoff, then verify its repository path,
   branch, HEAD, staged changes and untracked files before modifying anything.
2. Read the parent and active issue, their current owners, and the repository
   instructions. Follow the current-document route instead of rereading all
   historical research or conversation.
3. Identify one observable acceptance boundary and the evidence missing for it.
   Do not infer completion from an earlier agent's confidence, a checkpoint,
   code volume, or a passing test that covers a smaller scope.
4. Preserve the existing worktree and index. Record source and evidence identity
   at a checkpoint; never restore, clean or reset mixed work to simplify a task.

## Active implementation slices

The assigned implementer owns implementation, diagnosis, verification and
authorized Git/PR work, and resolves routine questions from current owners and
code. Review covers completed bounded changes and consequential unresolved
design gaps; it is not an approval checkpoint for routine steps or individual
test failures. Before escalating, the implementer checks authoritative sources
and supplies the specific contradiction, evidence and a reviewable proposal.
Assignments belong to the active task, not to model names in repository policy.

A component needed by another issue can be implemented earlier within the
accepted contract. Record that dependency in the owning issue and dependency
map. This does not waive the predecessor's acceptance obligations or authorize
implementation beyond the selected issues and count under the
[repository C0 work-in-progress policy](../../AGENTS.md#c0-work-in-progress-limit).
Each implementer retains one active slice with separate ownership and a worktree
or branch.

Keep one concrete next result. If a defect blocks it, diagnose and repair that
owner before adding another feature. An exhausted observation timeout does not
prove a test stopped: poll its known handle or inspect authoritative state.

A consequential gap in authority, protocol, privacy or a selected budget goes
back to design with the exact contradiction and a reviewable proposal. Keep
independent admitted work explicit rather than silently expanding the scope.

## Validate and retain a coherent result

- Reproduce meaningful failures at the real owner boundary. Fixtures may isolate
  scheduling or unavailable qualification boundaries only when those limits are
  stated; they cannot supply missing product mechanisms.
- Run the required quick checks while coding and the complete gate before
  integration. Re-run affected checks after a fix; do not repeatedly broaden
  unchanged passing tests without a concrete reason.
- Keep failed attempts and their source identity. A later pass is a correction,
  not permission to erase the earlier result.
- Update current factual owners with the implementation. Commit each coherent
  verified result separately while preserving unrelated staged or untracked
  work. A ready branch commit is not integration into main.
- Close an issue only when every acceptance and integration obligation is met.
  Missing prerequisites, incomplete consumers and deadcode failures stay visible.

## Progress communication

At a meaningful change, report the same concise state in the active conversation
and the owning GitHub record, within the user's authorized publication scope:

- active issue and acceptance criterion;
- criterion completed, evidence identity and coverage limits;
- criterion remaining or exact blocker;
- next observable result.

Use distinct states: in progress, verified locally, awaiting integration, and
accepted/integrated. Do not use an invented completion percentage or count code
changes as a delivered user journey. Keep the parent plan consistent with the
active child assigned to that implementer.

Do not publish raw captures, local secrets or sensitive operational details.
If automatic approval review rejects a write, report the exact action and
reason, preserve the prepared payload, and follow the review's allowed safer
alternative or obtain the necessary authorization. Do not bypass a rejection
through another tool or endpoint.

## Transfer to a fresh agent session

Finish or explicitly transfer each live tool/process handle. Save a compact
handoff outside the repository with paths to the actual worktree, checkpoint,
evidence and exact next defect/test; link to authoritative issue/owner contents
instead of duplicating them. Include the selected model, suggested skills and
unresolved approval boundaries.

Only the receiving session implements after handoff. The outgoing session may
coordinate and verify status, but must not edit concurrently. Transfer does not
complete the parent goal or authorize closing its issues.
