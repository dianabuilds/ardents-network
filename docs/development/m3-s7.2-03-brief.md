# Proposed M3-autonomous brief — S7.2-03 pre-stop refusal

Status: **engineering contract accepted by Codex under Product Owner standing
delegation on 2026-08-21; implementation remains blocked by S7.2-02.**
This brief becomes executable only after S7.2-02 is accepted and Codex replaces
the provisional scope caps with a factual post-S7.2-02 inventory.

## Why an amendment is required

The accepted task contract fixes the input classes and broad taxonomy, but it
does not yet fix:

1. the exact outcome for every row;
2. whether resource admission claims an operating-system quota reservation or
   a bounded pre-stop availability observation; or
3. how inode/entry availability is represented on Windows, where there is no
   portable free-inode counter equivalent to Unix `statfs`.

M3 must not invent any of these answers.

## Accepted engineering decisions

### D1 — exact refusal table

The first matching predicate wins in the order shown. Every result has a
non-nil error, the fixed safe notice shown below, no custody text derived from
the rejected candidate, and no dynamic operating-system text in `Result`.

| Input or observation | Outcome / state | Fixed safe notice |
|---|---|---|
| candidate bytes do not match the length/digest of an otherwise accepted Decision | `staging-failed/release-accepted` | `update staging failed` |
| observed short write or read-back mismatch after the source bytes passed length/digest verification | `staging-failed/artifact-verified` | `update staging failed` |
| candidate write, close, or candidate-data flush fails | `staging-failed/artifact-verified` | `update staging failed` |
| staging-directory publication or parent durability fails on an otherwise admitted filesystem | `staging-failed/artifact-verified` | `update staging failed` |
| root, staging, transaction, or activation parent has an insecure owner/mode/DACL | `activation-unsupported/release-accepted` | `update storage unsupported` |
| any admitted component is a symlink, junction, reparse point, hard link, mount alias, or changes identity during inspection | `activation-unsupported/release-accepted` | `update storage unsupported` |
| filesystem/volume kind is outside the R-050 allowlist or activation would cross a filesystem/volume | `activation-unsupported/release-accepted` | `update storage unsupported` |
| an exact coherent interrupted transaction already owns the staging slot | `resource-denied/<its last durable state>` | `update recovery required` |
| a fourth retained payload would be created, or the exact resource observation is below the required envelope | `resource-denied/release-accepted` | `update resources unavailable` |
| accepted candidate length is `67,108,865` or greater | `resource-denied/release-accepted` | `update resources unavailable` |
| unknown owned-root child or contradictory existing transaction evidence | `transaction-invalid/transaction-invalid` | `update transaction invalid` |

An unaccepted Release Decision remains S7.1 `release-invalid`; D1 does not
reclassify release verification. The wrong-digest row means that an otherwise
complete value with `Outcome=release-accepted` is paired with different
candidate bytes at the transaction boundary. As a defence-in-depth exception,
an `Outcome=release-accepted` value whose declared or observed candidate length
exceeds `67,108,864` is the explicit `resource-denied/release-accepted` ceiling
row. That does not claim Release Decision could normatively produce the forged
oversized value.

Result physical fields are frozen as follows:

- candidate mismatch and oversize rejection occur before root inspection and
  report the requested generation, zero digests, no staging, and no custody;
- a coherent capacity refusal or staging-operation failure reports the request
  generation, verified predecessor current/rollback digests, no staging after
  successful cleanup, and custody from that predecessor manifest;
- coherent interrupted staging reports its verified transaction generation,
  selected current/rollback digests, actual staging presence, and custody from
  the selected current manifest, and mutates nothing;
- inability to prove owner, mode/DACL, link, filesystem, or volume identity
  reports the request generation but zero physical digests, no staging claim,
  and no custody;
- `transaction-invalid` retains the accepted all-zero invalid shape; and
- any cleanup failure or overrun replaces the primary row with the accepted
  `cleanup-incomplete/<last coherent state>` shape and makes no physical claim.

Pre-existing staging is never part of the new request's cleanup. A staging
object without the exact coherent journal/current relationship is contradictory
evidence and therefore `transaction-invalid`, not a capacity refusal.

### D2 — resource admission is an observed lower bound

S7.2 does not claim an exclusive filesystem quota, and it does not claim that
free space elsewhere on the volume cannot change after inspection. Before the
first transaction directory, journal entry, or staging object is created,
`Apply` performs one native availability observation while holding the permanent
root lock. It compares that observation with the exact remaining transaction
envelope. Passing the check means only:

> at the observation point, the admitted filesystem reported at least the
> transaction's calculated byte and object requirements; later external disk
> pressure remains a staging/activation failure and never authorizes mutation of
> current work.

The calculation uses the filesystem allocation unit, rounds each future regular
file independently, and includes:

- the exact candidate artifact and authenticated manifest;
- all still-unpublished canonical journal records for this transaction;
- one bounded current-record replacement file;
- every still-uncreated transaction, journal, staging, and temporary directory
  entry;
- the exact copy-on-write byte/entry request when a later schema Adapter declares
  one; S7.2-03's existing `no-op-v1` plan contributes zero; and
- no bytes for current or rollback payloads that are already present and
  verified, because S7.2 activation renames rather than copies them.

The observation and arithmetic are private Implementation. Tests may call one
private per-invocation `applyWithResourceObservation` seam carrying only the
native observation values and allocation unit. Public `Apply` always uses the
native observer. There is no exported resource Interface and no package-global
fault state.

Arithmetic is checked and overflow fails `resource-denied` before allocation.
The accepted boundary passes when available values equal the calculated
requirements and fails on the first byte or object below them.

For `no-op-v1` at a fresh V0 root, required allocated bytes are exactly:

```text
round(candidate length, allocation unit)
+ round(canonical manifest length, allocation unit)
+ 9 * round(16 + 123, allocation unit)
+ round(canonical successor current-record length, allocation unit)
```

The `16`-byte record envelope and `123`-byte journal-v1 body are frozen by
`stage-7-s7.2-transaction-format-proposal.md` section 9, so every complete
journal entry is exactly `139` bytes. A schema divergence is `scope-blocked`;
the implementation must not silently recalculate a different journal-v1 size.

The object lower bound is exactly `15`: transaction and journal directories,
the staging temporary directory, artifact and manifest files, nine journal
files, and one current temporary file. Existing root, `staging`, `transactions`,
`generations`, current, marker, permanent lock, and selected payload objects are
not counted again. Directory metadata blocks are not claimed by the byte
formula. The test oracle precomputes manifest/current lengths independently;
production arithmetic is not its oracle.

### D3 — platform resource and storage evidence

- On Linux, every admitted path component and opened object has the process
  effective UID. Owned directories have exactly `0700`; owned regular files
  exactly `0600` and link count one. The observer requires
  `EXT4_SUPER_MAGIC`, equal `st_dev`, and one equal mount ID obtained from one
  read-only `/proc/self/mountinfo` snapshot. That snapshot is at most `1 MiB`,
  `4,096` lines, and `4,096` bytes per line; excess, malformed escapes, duplicate
  mount IDs, or unprovable device facts are unsupported. The parser decodes the
  mount-point field, selects the longest component-boundary prefix for each
  admitted absolute path, requires `fstype=ext4`, requires the entry's
  `major:minor` to equal that object's `st_dev`, and requires the selected mount
  ID to equal the root mount ID. A nested bind mount therefore fails even when
  it shares the same device. It uses `Bavail * Frsize` bytes and `Ffree` objects
  with checked multiplication/addition. Final activation revalidation repeats
  the identity observation; the first snapshot is not claimed to freeze the
  host mount namespace.
- On Windows, root owner is the process `TokenUser`. Its non-null DACL is
  protected and has exactly one explicit `GRANT_ACCESS` owner ACE with
  `GENERIC_ALL` and object/container inheritance. Descendants have only the
  exact inherited owner equivalent; no other allow/deny trustee is admitted.
  Every object is opened without following reparse points and has one link when
  regular.
- On Windows, the native observation uses fixed-volume free-byte and allocation-
  unit facts. It requires filesystem name exactly `NTFS`, drive type
  `DRIVE_FIXED`, and one equal volume serial/root identity for every admitted
  object. The exact object count remains an internal envelope ceiling, but the
  production observer reports no free-object capacity and makes no free-inode
  claim. The private seam may test checked object-count arithmetic but cannot
  manufacture a native Windows `resource-denied` object-capacity observation.
  A Windows object-create refusal after byte admission is `staging-failed`.
- Native admission supports only the R-050 development surfaces: same fixed NTFS
  volume on Windows and same ext4 mount on Ubuntu. SMB/NFS, OverlayFS,
  tmpfs, FUSE, ReFS, FAT/exFAT, removable, cross-mount, and
  cross-volume roots return `activation-unsupported`.
- Linux admits a mount only when both the mountinfo filesystem type is exactly
  `ext4` and `statfs` reports `EXT4_SUPER_MAGIC`; a FUSE-mounted ext image fails
  this same allowlist predicate and returns `activation-unsupported`.
- Ubuntu Docker may exercise logical ext4-backed-volume behavior but remains a
  development Adapter test, not native reboot, power-loss, disk-full, or
  inode-full qualification.

"Cloud-synced" is a deployment precondition, not a reliably discoverable
filesystem property. The Module rejects a storage kind or mount it can prove is
outside the allowlist; it makes no claim that platform APIs can identify every
third-party synchronization agent. A capacity-observer failure after storage
identity was proved is `resource-denied`; inability to prove identity is
`activation-unsupported`.

### D4 — atomic staging publication and recovery extension

The fixed rename-failure row requires a real pre-stop publication boundary.
For S7.2-03, staging is written only under
`staging/<generation>.tmp`, whose admitted contents are exactly `artifact` and
`manifest.bin`. After both direct regular files are completely written,
flushed, closed, independently read back, and matched, the Module renames that
directory in the same parent to `staging/<generation>` and acknowledges the
`staging` parent. Only then may it publish the `staged` journal entry.

No other temporary name is admitted. The source and destination cannot coexist.
A crash or failure before the directory rename leaves only the exact declared
temporary tree; a crash after rename and before the `staged` entry is the
existing unacknowledged-staging case. These supplemental S7.2-03 recovery rows
do not change journal bytes and are required by its accepted
"declared incomplete staging is removed within 5 s" criterion. They do not
change any S7.2-02 R00-R14 input or expected result; the complete final staging
row is the existing R03, while the exact temporary-tree row is new evidence
that can exist only after S7.2-03 introduces that publication boundary.

| Last durable state | Physical staging fact | Normalization |
|---|---|---|
| `artifact-verified` | exact partial or complete `<generation>.tmp`, no final staging | remove only that exact temp deepest-first with parent acknowledgement; return `recovered/artifact-verified` |
| `artifact-verified` | exact complete final `<generation>`, no temp | remove only that exact unacknowledged candidate; return `recovered/artifact-verified` |
| any other prefix or both names | any temp presence | `transaction-invalid`, no mutation |

Failure or overrun of this normalization returns the accepted
`cleanup-incomplete/artifact-verified` shape. A symlink, reparse point, hard
link, unknown child, wrong generation, or content not bound to the journal is
invalid and never cleanup input.

### D5 — narrow test-only operation seams

Tests may inject one private per-invocation stage-operation value containing
only exact candidate-file write, file flush/close, directory rename, and parent
acknowledgement operations. They may also inject one admission-checkpoint
callback immediately before the final owner/link/filesystem revalidation to
produce an identity-swap observation. Public `Apply` always supplies native
operations and a no-op checkpoint.

Neither seam may replace root inventory, path parsing, security predicates,
resource arithmetic, journal encoding, cleanup planning, clocks, outcomes, or
Results. There is no context value, package-global mutable state, generic
filesystem mock, retry, or second operation attempt. Cleanup/failure injection
continues to use only the S7.2-02 typed per-invocation cleanup operations.

## Frozen execution order

For a new transaction, public `Apply` performs the following before any
`WorkControl` call:

1. validate the accepted Decision and bounded candidate shape;
2. acquire and verify the permanent root lock;
3. perform one non-mutating root/selection/storage admission pass;
4. reject an existing staging slot, excess retained payload, unknown entry, or
   contradictory transaction;
5. calculate and compare the exact resource envelope;
6. create the transaction/journal tree and publish `release-accepted` and
   `artifact-verified`;
7. stage, byte-verify, flush, and durably publish the candidate;
8. publish `staged` and `rollback-reserved`; and only then
9. call `StopNewWork`.

Every D1 refusal occurs before step 9. Refusal before step 6 performs no
transaction cleanup because it created nothing. Failure during steps 6–8 uses
the accepted five-second cleanup continuation and exposes no partial generation
or activation replacement.

## Independent test oracle

The red test table constructs the V0 predecessor and accepted Decision from
saved bytes, then changes exactly one input fact. Expected outcomes and resource
arithmetic are literal test data or a test-only encoder; tests do not call a
production validator, resource calculator, hash helper, result constructor, or
summary to derive expectations.

Every row proves:

- `StopNewWork`, `Drain`, and `SelfTest` call counts are zero;
- `current`, current artifact, current manifest, rollback, Vault probe, and
  floor probe are byte-identical;
- no candidate generation exists under `generations`;
- only the declared incomplete staging/transaction prefix may have existed, and
  it is removed within the cleanup continuation;
- the permanent lock remains the same direct empty single-link file; and
- repeated inspection reports the same bounded refusal without accumulating
  files, handles, goroutines, or timers.

Minimum rows are every D1 row, exact `67,108,864` success through
`rollback-reserved` with an injected stop before `StopNewWork`, first-byte
excess, equality/first-byte-below/first-object-below resource boundaries, and
one native Windows storage-admission test plus the authorized Ubuntu Docker
logical ext4-backed test. Native Ubuntu host qualification remains deferred to
the clean-host campaign and is not inferred from Docker.

## Allowed scope and provisional caps

Production scope is limited to `internal/updatetransaction` resource admission,
storage admission, staging, result mapping, and their platform files. Caller
production changes are allowed only if an already-required D1 outcome cannot be
rendered by the existing bounded JSON mapper. No exported declaration, package,
command, new module dependency, record format, journal state, retry, queue, or
activation behavior may be added. The already recorded `golang.org/x/sys`
dependency may be used through its platform-specific Windows package for DACL
and handle evidence; `go.mod` and the accepted dependency version remain
unchanged.

The accepted common caps remain hard: at most 15 changed files, 1,500 net new
production LOC, 500 lines per Go file, and one implementation commit. A
production file above the 250-line review threshold requires the accepted
cohesion evidence. Before authorization, Codex records the S7.2-02 final
physical inventory and freezes stricter task-local file/LOC caps. Crossing any
conjunctive cap is `scope-blocked` without a commit.

## Mandatory gates

The implementation runs focused Module tests throughout, then:

```text
go test ./internal/updatetransaction -count=1
go test -race ./internal/updatetransaction -count=1
GOOS=linux GOARCH=amd64 go build ./internal/updatetransaction ./cmd/ardents-release
GOOS=windows GOARCH=amd64 go build ./internal/updatetransaction ./cmd/ardents-release
authorized Ubuntu 26.04 Docker tests
make quick-check
make check
```

Native disk-full, inode-full, reboot, and hard-power claims remain environment-
deferred. Windows installation or host mutation still requires a separate
Product Owner command.

criterion-to-test map, exact commands/results, limitations, and scope
confirmation, and ends exactly:
