# S7.2 production-file size amendment

Status: **accepted by Product Owner and Codex on 2026-08-21**

Owner decision required: **no**

Applies to: maintained Go code and every remaining S7.2 task

## Accepted decision

Replace the universal `250`-line production-file hard cap. Evidence from
S7.2-01 and S7.2-02 shows that the cap is not a reliable quality gate: it
rewards mechanical file splitting, moves one state machine across several
files, increases private choreography, and can still leave correctness defects
behind a green size check.

This amendment does not accept large files by default. It changes file size
from a proxy for design quality into a review signal, while preserving an
interim absolute bound until Stage 8 G2 accepts the complete engineering
policy.

## Accepted rule

1. `250` physical lines is a **review threshold**, not an executable failure.
2. The existing `500`-line limit for every Go file remains an interim absolute
   bound through Stage 7.2. Stage 8 G2 may replace it with the complete hotspot
   policy.
3. A production file over 250 lines is acceptable only when it owns one named,
   cohesive implementation responsibility and splitting it would separate
   invariants or increase cross-file choreography.
4. A review of such a file records:
   - its single responsibility;
   - the invariants that benefit from locality;
   - why the obvious split would make the Module shallower or harder to verify;
   - the behavior tests that exercise it through the Module Interface; and
   - any real hotspot found in branching, nesting, fan-in/fan-out, duplication,
     exported surface, or unrelated concepts.
5. Review requires a split when responsibilities can vary independently, have
   different platform or dependency constraints, or are easier to understand
   and verify as separate private implementations. A split must not create a
   new public Interface merely to satisfy file size.
6. Catch-all filenames remain forbidden. File names still describe one
   implementation responsibility.
7. Task-specific total production LOC, changed-file count, package admission,
   permitted imports, command ownership, and thin-command limits remain hard
   where their accepted contract states them. Per-production-file values in
   S7.2 task tables become planning targets and review triggers, not acceptance
   caps.
8. A task cannot claim `implemented` merely because its files are below a size
   threshold. Acceptance continues to require its frozen oracle, behavior
   tests, platform evidence, error observation, resource bounds, and repository
   gates.

## Executable-gate change

- `internal/architecture/architecture_test.go` stops rejecting a production
  file solely because it exceeds 250 lines;
- the interim all-Go 500-line failure remains;
- `AGENTS.md`, `go-engineering.md`, and `repository-layout.md` receive the same
  wording so instructions and executable policy cannot disagree; and
- accepted and proposed S7.2 contracts replace their 250-line acceptance cap
  with the review-threshold rule above.

An executable test cannot determine cohesion. The architecture gate therefore
checks facts it can prove, while the task contract and independent review own
the design judgment.

## Immediate effect on S7.2-02 Gate B

The frozen Gate A tests and every behavioral acceptance criterion remain
unchanged. M3 may continue an already named implementation responsibility past
250 lines, but not past 500 lines, only after the controller records the review
rationale. No production commit is allowed until the complete Gate B passes
independent review and the required repository gates.

The three partial Gate B production files are not grandfathered. Lock identity,
bounded inventory reads, complete physical enumeration, interrupted-transaction
selection, cleanup error observation, and platform behavior are correctness
requirements independent of file size and must still be reviewed and fixed.

## Evidence and scope boundary

- S7.2-01 twice reached `scope-blocked`; expanding the file count did not fix
  missing tests, idempotency, predecessor commitments, Adapter injection, or D0
  verification.
- S7.2-02 Gate B began producing additional files shaped around the 250-line
  ceiling before its recovery behavior was complete.
- The Stage 8 design workbook already schedules G2 to replace
  architecture-by-line-count with responsibility, cohesion, navigation, and
  soft hotspot signals.

This amendment decides the narrow Stage 7.2 rule. It does not pre-accept the
complete Stage 8 G2 engineering policy.
