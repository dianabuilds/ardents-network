# Proposed M3-autonomous brief — S7.2-04 bounded drain and activation

Status: **engineering contract accepted by Codex under Product Owner standing
delegation on 2026-08-21; implementation remains blocked by S7.2-03.**
It becomes executable only after S7.2-03 is accepted and implemented and Codex
freezes factual post-S7.2-03 file/LOC caps.

## Why an amendment is required

The task table currently cannot be implemented without inventing policy:

- `Request.ActiveWork` is rejected unless zero, while the task requires live
  work;
- no credential deadline crosses the Interface, and that deadline belongs to
  the later Contributor task S7.2-07;
- the local 15-second calculation and late-return behavior are unspecified;
- activation busy has no lifecycle outcome in the existing taxonomy;
- the general format text appears to require a failed Adapter journal entry,
  but R00-R14 admit only successful prefixes and V0 freezes `activated` with
  `adapter-not-called`; and
- static unsupported storage is already a pre-stop S7.2-03 refusal.

M3 must not resolve these ambiguities.

## Accepted engineering decisions

### D1 — bounded work is caller-owned

`Request.ActiveWork` is a bounded caller-declared observation, not independent
security evidence. S7.2-04 accepts `0` or `1`; later tasks may amend the bound
only with their own accepted contract. The caller-owned `WorkControl` remains
responsible for rejecting new admission after successful `StopNewWork` and for
closing its accepted work during `Drain`.

`ActiveWork > 1` is an invalid bounded request, not evidence of resource
exhaustion. It returns the accepted all-zero
`transaction-invalid/transaction-invalid` shape before root inspection,
mutation, or any `WorkControl` call.

The Update Transaction proves only that it:

1. calls `StopNewWork` exactly once;
2. durably publishes one `stop-new-work` entry containing success or bounded
   failure after that call returns;
3. never calls `Drain` before a durable successful `stop-new-work` entry;
4. calls `Drain` exactly once; and
5. never starts activation after either call fails, returns late, or exceeds its
   context deadline.

An Interface test Adapter exposes a test-only admission attempt and proves it is
rejected after `StopNewWork`. The existing `apply-offline` caller remains a
zero-work stopped-runtime Adapter. S7.2-04 makes no claim that an unselected live
runtime has been integrated.

### D2 — exact deadline algorithm

Public `Apply` captures one `time.Now()` value at function entry. That Go
`time.Time` carries the invocation's wall value and in-process monotonic
reading. The local deadline is `invocationStart.Add(15 * time.Second)`; the
caller context deadline is also captured once at function entry and is never
resampled or extended:

```text
local = invocation start + 15 seconds
stop  = min(caller deadline, build terminate, protocol transition,
            build no-new-work, local)
drain = min(caller deadline, build terminate, protocol transition, local)
```

A zero protocol-transition deadline is absent. Credential, assignment, epoch,
and role deadlines are not inputs to S7.2-04; they remain S7.2-07 work.

Both Adapter calls are synchronous and receive their exact bounded context.
There is no goroutine wrapper, retry, or replay. After an Adapter returns,
`ctx.Err()` has priority over a nil return; a late success cannot publish the
state or begin the next operation. Tests use a private per-invocation monotonic
clock seam only to supply the one invocation-start value and subsequent
monotonic observations; public `Apply` supplies the native clock.
`WorkControl` is a trusted caller-owned Adapter and must return when its context
is done. This slice proves the deadline passed to a cooperative Adapter; it does
not claim that Go can forcibly terminate a malicious Adapter without leaking a
goroutine or process.

### D3 — exact result table

| Observation | Outcome / state | Error | Fixed safe notice |
|---|---|---|---|
| zero work, or one item drains before the earliest deadline, then activation and existing V0 self-test succeed | `committed/committed` | nil | `update committed` |
| `StopNewWork` fails, reaches its deadline, or caller cancellation wins | `drain-expired/rollback-reserved` | non-nil | `update drain expired` |
| `Drain` fails, reaches its deadline, returns nil after expiry, or caller cancellation wins | `drain-expired/stop-new-work` | non-nil | `update drain expired` |
| supported Windows activation reports one sharing/lock/delete-denial busy result before replacement | `activation-busy/draining` | non-nil | `update activation busy` |
| final owner/mode/DACL/filesystem/volume revalidation becomes unsupported after S7.2-03 admission and before replacement | `activation-unsupported/draining` | non-nil | `update storage unsupported` |
| replacement may have completed but its durability or post-publication identity cannot be normalized by the accepted R10/R11 rule | `transaction-invalid/transaction-invalid` | non-nil | `update transaction invalid` |
| abort cleanup fails or overruns | accepted `cleanup-incomplete` shape at the last coherent state | non-nil | `update cleanup incomplete` |

The successful row reuses the already accepted S7.2-01 vertical tracer after
S7.2-04 replaces its zero-work stub behavior; S7.2-04 does not add self-test or
commit semantics and does not claim the S7.2-05 negative paths.

The four ordinary bounded refusals are the failed/expired stop row, the
failed/expired drain row, activation busy, and activation unsupported. They
report the request generation, predecessor
current digest, prior rollback digest if one existed, no staging after successful
abort cleanup, and custody from the predecessor manifest. `transaction-invalid`
and `cleanup-incomplete` retain the zero-field rules accepted in S7.2-02.

`activation-busy` is added to the lifecycle outcome registry because R-050 uses
that exact outcome. It is not silently collapsed into root-lock
`resource-denied/busy`.

### D4 — journal v1 records the bounded Adapter result

S7.2-04 follows the accepted format rather than narrowing it. An Adapter is
called before its state entry is published, and the entry records success or
bounded failure:

- failed stop publishes `stop-new-work` with `adapter-failed`; the public Result
  still names `rollback-reserved` as the last successful state;
- failed drain publishes `draining` with `adapter-failed`; the public Result
  still names `stop-new-work` as the last successful state;
- activation busy publishes `activated` with `adapter-busy`, while the public
  Result names `draining` and the predecessor selection remains current;
- activation revalidation failure publishes `activated` with
  `adapter-unavailable`, while the public Result names `draining`; and
- successful stop and drain keep `adapter-success`.

Successful private activation keeps the frozen V0 `adapter-not-called` byte.
M3 must not rewrite it to `adapter-success`. No record length, canonical V0
byte, successful R00-R14 input, or predecessor commitment changes in this task.

S7.2-04 extends recovery only for these exact failure-coded prefixes. With no
`WorkControl` call, recovery executes the same deterministic abort plan and
returns the corresponding bounded D3 refusal. A missing, mismatched, repeated,
or failure-coded entry in any other state is `transaction-invalid` and
byte-preserving. Cleanup failure or overrun returns the accepted
`cleanup-incomplete` shape. Existing successful R00-R14 rows remain unchanged.

### D5 — abort, retry, and uncertain publication

After an ordinary post-stop refusal, `Apply` runs one abort plan under the shared
five-second cleanup continuation. It removes only the candidate generation,
staging, and incomplete transaction journal declared by that plan in
deepest-first lexical order with the required parent acknowledgements, restores
or preserves the predecessor selection first, and makes no `WorkControl` call.
It never reopens admission or claims a failed Adapter's external state. After a
successful `StopNewWork`, caller work remains stopped until external reset. If
any step fails or overruns, the remaining evidence is retained and the result
is `cleanup-incomplete`; a new Apply is not admitted over that residue.

Abort cleanup uses the accepted independent five-second continuation even when
the caller context caused the primary stop/drain refusal. Caller cancellation
does not cancel or shorten cleanup. If cleanup completes, the primary D3 result
is returned; only a cleanup-operation failure or its own five-second overrun
replaces that result with `cleanup-incomplete`.

A later attempt is a new explicit caller invocation after complete abort cleanup
and external work-control reset. Because the failed generation was never
committed, the caller resubmits the same required
`current.Transaction + 1` generation; changing the candidate or Decision starts
a different explicit episode but does not skip the generation. There is no
internal activation retry, automatic `Apply`, or Application operation replay.

If atomic replacement may have happened, `Apply` uses the same physical
inspection and predecessor reconstruction as S7.2-02 R10/R11 before reporting an
ordinary refusal. If the physical state cannot be normalized exactly, it returns
`transaction-invalid` without guessing that old or new is current.

### D6 — activation Adapter classification

Static unsupported/cross-volume roots remain S7.2-03 and fail before
`StopNewWork`. The S7.2-04 unsupported row is a TOCTOU revalidation failure after
that admission.

Activation still performs the R-050 sequence:

- publish the already verified staging directory as one immutable generation;
- write and flush one same-directory bounded current temp;
- atomically replace `current` on the same admitted filesystem/volume;
- durably acknowledge its parent and reverify handle/path/owner/mode or DACL.

Only atomic current replacement changes live selection. There is no in-place or
cross-volume fallback.

On Windows, after successful DACL/owner/volume revalidation,
`ERROR_SHARING_VIOLATION`, `ERROR_LOCK_VIOLATION`, and a held-delete-handle
`ERROR_ACCESS_DENIED` before replacement map to `activation-busy`. A failed
DACL/owner/volume predicate maps to `activation-unsupported`. Linux receives no
synthetic busy fallback. On Linux, a failed owner/mode/mount/filesystem
predicate after S7.2-03 admission maps to
`activation-unsupported/draining` with `update storage unsupported`.

### D7 — exact task-contract amendment

On acceptance, S7.2-04 acceptance criterion 1 is replaced with:

> Every `StopNewWork` attempt is durably recorded before any `Drain`. A
> successful stop rejects later admission; a failed or expired stop never calls
> `Drain`.

The fixed input row `credential deadline earlier than both` is replaced by an
earlier caller, Build Safety, or protocol-transition deadline. No credential or
role deadline exists at this Interface before S7.2-07.

## Independent red oracle

Tests cross public `Apply` for every ordinary row. Private per-invocation seams
may supply only the monotonic clock and an exact platform activation result;
public `Apply` always supplies native dependencies. No package-global mutable
fault, context value, exported test Interface, or generic filesystem mock is
allowed.

Every negative row proves:

- exact Adapter call order and count;
- old current bytes remain readable and byte-identical unless R10/R11
  normalization was required;
- self-test is not called;
- no later state entry, retry, or replay exists;
- the exact abort inventory and five-second continuation result; and
- permanent lock identity and D0 probes are unchanged.

The 15-second calculation test injects one exact invocation-start `time.Time`
and proves that the Adapter context deadline equals the minimum of that value
plus 15 seconds and the frozen caller/authenticated deadlines. It does not
sleep for 15 seconds. Expiry uses a deliberately earlier bounded
caller/authenticated deadline.

The concurrent-reader oracle performs at least 100 reads spanning replacement;
each read independently decodes as the complete old or complete new current
record, never missing, partial, mixed, or oversized. The Windows held-delete
row performs exactly one activation attempt and proves exact busy with no retry.

## Scope and provisional caps

Allowed production work is limited to `internal/updatetransaction` drain,
activation classification, abort planning, and narrow existing caller comments
or result rendering only when required by D3. No new package, command,
dependency, exported declaration, record version, journal state, or caller
production work controller is allowed.

The common 15-file/1,500-production-LOC and interim 500-line all-Go caps remain
hard; production files above 250 lines require the accepted cohesion review.
Before authorization Codex records the accepted S7.2-03 inventory and
freezes stricter per-task files and LOC. Crossing a conjunctive cap is
`scope-blocked` without a commit.
