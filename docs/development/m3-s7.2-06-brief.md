# Proposed M3-autonomous brief — S7.2-06 copy-on-write schema commit

Status: **engineering contract accepted by Codex under Product Owner standing
delegation on 2026-08-21; implementation remains blocked by S7.2-05a/05b.**
This brief becomes executable only after S7.2-05a/05b is implemented and
accepted, the authoritative task/format documents and C7 vector are amended in
one implementation-authorizing commit, and Codex replaces the provisional caps
with a factual post-S7.2-05 inventory.

The future implementation handoff is `M3-autonomous`; independent review is a
fresh `M3-after-contract` context. Until the gates above pass, the task is
`contract-blocked` and the implementation verdict is **NO-GO**.

## Why an amendment is required

The accepted S7.2-06 task says what must be preserved but does not determine an
implementation. In particular:

- the seven-declaration Interface has no schema Adapter or bounded schema value;
- the exact copy-on-write plan, owner, source, destination, and fixture format
  are not frozen;
- `current` already selects candidate **code** at `activated`, while the old
  mutable schema must remain selected until `committed`;
- manifest v1 accepts only `no-op-v1`, and journal v1 has no schema commitments;
- `Result` has no schema digest, byte-count, or entry-count fields;
- `Recover(context.Context, string)` has no foreign-owner Adapter and therefore
  can recover only the transaction-owned schema selection facts, not rescan a
  foreign Module's content after process restart;
- validation, publication, rollback, interruption, and cleanup outcomes are
  not exact; and
- D0 names foreign custody state, but no accepted production Adapter supplies
  those commitments to Update Transaction.

M3 must not fill these gaps. The design below keeps the whole-transaction
`Apply`/`Recover` operations, keeps schema bytes outside the Update Transaction
root, and adds the smallest coherent Apply-side Adapter seam. `Recover` proves
only canonical journal and selection-record facts owned by Update Transaction.
It does not claim a fresh foreign-root readability observation; the next
explicit Apply/idempotency inspection or runtime self-test performs that check.

## Accepted engineering decisions

### D1 — exact plans and minimal Interface amendment

The only accepted plan literals are:

- `no-op-v1` — preserve the selected schema and all V0 bytes; and
- `copy-on-write-v1` — copy the exact selected schema fixture, change only its
  schema version from `1` to `2`, validate the complete copy, and select it only
  at transaction commit.

Add exactly two exported declarations:

```go
type SchemaSelection struct {
	Owner      [32]byte
	Generation uint64
	Identity   [32]byte
	Content    [32]byte
	Bytes      uint64
	Entries    uint64
}

type SchemaWork interface {
	Plan(context.Context, uint64, string, SchemaSelection) (candidate SchemaSelection, resourcesAdmitted bool, err error)
	Prepare(context.Context, SchemaSelection) error
	Inspect(context.Context, SchemaSelection) error
	Discard(context.Context, SchemaSelection) error
}
```

`Request` gains `Schema SchemaWork`; `CandidateIdentity` gains
`Schema SchemaSelection`. No other exported declaration, method, constructor,
sentinel, enum, callback, path, or byte slice is added. `Apply` and `Recover`
retain their exact signatures; `Recover` receives no Adapter, schema path, or
generic filesystem. Once the prerequisite S7.2-05 unavailable type is accepted,
the resulting Module surface is exactly ten declarations: `WorkControl`, `SelfTest`,
`SelfTestUnavailable`, `CandidateIdentity`, `Request`, `Result`,
`SchemaSelection`, `SchemaWork`, `Apply`, and `Recover`. `Result` and
`ardents-update-result-v1` remain byte-compatible and do **not** surface schema
identity, digest, bytes, entries, or a path.

`Request.Schema == nil` is valid **only** when the inspected update root has no
`schema-current` and the exact plan is `no-op-v1`. That is the legacy V0 case:
the zero predecessor remains implicit, no Schema method is called, and its
manifest, journal, Result, and command JSON are unchanged. Nil is
`transaction-invalid` for `copy-on-write-v1` and for every root that already
has `schema-current`. For
`copy-on-write-v1`, every method receives only bounded values; its concrete
Adapter closes over its own schema root. It receives no update-root path,
Vault/Authority path, floor path, root material, secret, Credential, Grant,
Network Epoch, Namespace, or mutator for another Module.

On a legacy root without `schema-current`, `no-op-v1` uses
`SchemaSelection{}` and journal v1: `Plan`, `Prepare`, `Inspect`, and `Discard`
are not called, and the root never gains a schema record. Once a COW transaction
has created `schema-current`, a later no-op must preserve and bind that exact
non-zero selection, uses manifest/journal v2, does not increment schema
generation, treats the candidate selection record as byte-identical to the
predecessor record, and calls `Inspect` before the new transaction can proceed.
It may not revert the root to the legacy zero form.

`Plan` is read-only and precedes resource admission. It verifies the selected
source, calculates the deterministic candidate, reports its exact logical bytes
and entries, and returns `resourcesAdmitted=false, err=nil` when its bounded
foreign-volume admission refuses the plan. Any non-nil error means the source
or plan is incompatible; `resourcesAdmitted` is ignored in that case. Its scan
stops at the first byte after `67,108,864`, the
first entry after `4,096`, or the first invalid object; it cannot enumerate an
unbounded foreign tree to learn that it is over the limit. Update Transaction
recomputes the selection identity from the other five fields and treats a
mismatch as `transaction-invalid`. A false admission or a descriptor above
the logical limits is `resource-denied/release-accepted` before mutation.
`Prepare` materializes exactly that candidate without
selecting it. `Inspect` fully reopens, validates, and recomputes one exact
selection without mutation; only Apply may call it. `Discard` may remove only
that unselected candidate. A different value, a nil
Adapter where the preceding rule requires one, a changed source, or a
non-idempotent repeated call is `transaction-invalid`.

### D2 — custody and the independent schema-selection fact

Schema content remains under the schema owner's root, outside
`<updateRoot>`. Update Transaction never opens, walks, copies, hashes, deletes,
or changes permissions in that root. Only the caller-owned `SchemaWork` Adapter
does so. Update Transaction owns one bounded selection fact because ADR-0015
assigns transaction commit to this Module:

```text
<updateRoot>/schema-current
```

This is independent of `current`:

- `current` selects immutable **code** and changes at `activated`;
- `schema-current` selects the schema owner's immutable copy-on-write
  generation and changes only at `committed`.

The future runtime schema owner must treat `schema-current` as its sole
selection fact
for this fixture profile. It resolves the opaque `Owner` and `Identity` inside
its own root; Update Transaction cannot resolve them. A COW-capable initialized
root must already contain one valid bootstrap `schema-current`. In S7.2-06 only
the independent test fixture creates that bootstrap: no production schema
owner or installer has been selected. Production COW is therefore unavailable
in this slice. S7.2-06 does not bootstrap, relocate, merge, or repair a foreign
root. Legacy no-op roots may omit the record. Once a root has one, later no-op
updates preserve and bind it.

The only additional transient update-root name is
`.schema-current.<16-lower-hex>.tmp`. It is a direct regular single-link sibling
on the same admitted filesystem. Symlinks, reparse points, hard links, aliases,
unknown names, a second temp, or a schema record inconsistent with the journal
fail closed.

It shares the update-root parent with `.current.<16-lower-hex>.tmp`, but the
distinct literal prefixes prevent collision even when the random suffixes are
equal.

### D3 — exact schema-current v1 record

Extend the existing private `ARDUPD01` envelope with kind `5`, version `1`.
Its body is exactly `160` bytes and the complete record exactly `176` bytes:

| Offset in body | Width | Field |
|---:|---:|---|
| 0 | 8 | selecting transaction generation |
| 8 | 32 | schema-owner commitment |
| 40 | 8 | schema generation |
| 48 | 32 | opaque selection identity |
| 80 | 32 | canonical content commitment |
| 112 | 8 | logical content bytes |
| 120 | 8 | logical entry count |
| 128 | 32 | SHA-256 of exact predecessor `schema-current`; zero only for bootstrap |

All integers are unsigned big-endian. Digests are raw 32-byte values. The
bootstrap record has transaction and schema generation `0`; a candidate has the
current transaction generation, schema generation exactly predecessor + 1,
the same non-zero owner, non-zero content and identity, bounded counts, and the
exact predecessor-record digest.

Kind `5` is bounded to exactly `176` bytes in version 1 and to the existing
`4,096`-byte inspection/journal record ceiling for decoder admission. A different
body length, trailing byte, version, flags value, or all-zero record where a
non-zero selection is required rejects.

Selection identity is not Adapter-chosen text. It is:

```text
SHA-256("ardents-schema-selection-v1\x00" ||
        owner[32] || be64(schema-generation) || content[32] ||
        be64(logical-bytes) || be64(entries))
```

No path, filename, dynamic error, secret, Authority/floor commitment, or schema
payload appears in this record.

### D4 — exact bounded COW fixture and canonical content

This slice proves one bounded development fixture, not a general database
migration tool or a claim about unbounded user data. The Adapter-owned root is:

```text
<schemaRoot>/
  .ardents-cow-schema-v1
  generations/
    <64-lower-hex selection identity>/
      schema-version
      entries/
        00000000.entry
        ...
  staging/
```

The marker is exact UTF-8 `ardents-cow-schema-v1\nowner=<64-lower-hex>\n`.
`schema-version` is exactly eight-byte unsigned big-endian `1` or `2`. Entry
names are contiguous lowercase eight-hex ordinals from zero. Each is one direct
regular single-link file. There are no links, sparse aliases, devices, nested
directories, unknown objects, or in-place writes.

Logical bytes are the sum of entry-file lengths; logical entries are the count
of entry files. Both the source and candidate must satisfy bytes
`<= 67,108,864` and entries `<= 4,096`. The first excess is
`resource-denied/release-accepted` before `Prepare`. Filesystem allocation,
directories, marker, version file, and durability temps are additional resource
admission costs; they are not falsely hidden inside logical bytes/entries.
`SchemaWork.Plan` owns bounded enumeration and reports/refuses those foreign-root
costs before `Prepare`; Update Transaction never estimates allocation in the
foreign root. A plan above either logical bound or a reported foreign-capacity
refusal is `resource-denied/release-accepted`. A real allocation or durability
failure after admission is schema staging failure, not a retroactive resource
decision.

Canonical content is SHA-256 over this exact byte sequence:

```text
UTF-8 "ardents-cow-schema-content-v1\n"
be64(schema-version)
be64(entry-count)
for each ordinal in increasing order:
    be64(ordinal) || be64(entry-length) || exact entry bytes
```

`copy-on-write-v1` copies every entry byte exactly, changes only the canonical
version from `1` to `2`, writes and flushes a fresh staging tree, atomically
publishes the complete immutable candidate under `generations/<identity>`,
syncs the parent, reopens every object, recomputes the canonical content and
descriptor, and still does not select it. An exact already-published candidate
is idempotent; a conflicting object is invalid. `Discard` removes only this
unselected generation and acknowledges the parent within the shared cleanup
budget.

The small frozen fixture uses owner seed
`ardents-cow-owner-fixture-v1\n`, entries `alpha\n` and `beta\n`, source schema
generation/version `0/1`, candidate generation/version `1/2`, and transaction
generation `1`. Independently computed values are:

| Fact | SHA-256 |
|---|---|
| owner commitment | `76a3178d1d3ca35f95c56b2e589ed26e296cc12e5f6603c6e7317cac86418b69` |
| source content | `bd2302c726244d84bdcb1cb48c1010f1109a8cd69a921597c63f5ff0504d3cb1` |
| candidate content | `edc0d9d9e624b2c8ca1edb3d8391047a78f5a2e760e6bf9fdf2d9b094c747e60` |
| source selection | `daa8c12c1676c96a5ababc196a9da601da4b99d29a0e70c919e1caa60ce30f36` |
| candidate selection | `b8ab53a406ed564f996aa17ff8ac26f8976432bc86c9cad013a90b7a335165b4` |

### D5 — manifest v2 and journal v2 are necessary and exact

Manifest v1 remains exactly the legacy zero-schema `no-op-v1` and is never
reinterpreted. A transaction with a non-zero schema selection uses manifest
kind `1`, envelope version `2`, with the same body field order and canonical
encoding rules as manifest v1. Version 2 accepts exactly `copy-on-write-v1` or a
schema-aware `no-op-v1`; stored `schema-compatible` is true only after the D1/D4
plan has succeeded. Every other version/plan pair rejects. The schema descriptor
is not duplicated in the manifest; its exact commitments live in the selection
record and journal.

Journal v1 and every V0 entry remain byte-identical. A schema-aware transaction
uses journal kind `4`, envelope version `2`. Its body appends exactly two fields
after the existing deadline:

1. SHA-256 of the exact predecessor `schema-current` record; and
2. SHA-256 of the exact candidate `schema-current` record.

The v2 body is `187` bytes and the complete entry `203` bytes. For a
schema-aware no-op both digests are equal. For COW they are D4's predecessor and
candidate record commitments. All entries in one chain use one journal version;
mixed versions reject. Existing state and Adapter-result codes, including the
proposed S7.2-05 codes 10-12, retain their meanings. The 4,096-byte entry and
16-entry transaction limits are unchanged.

For journal v2, the canonical predecessor-inspection body appends SHA-256 of
the exact decoded, coherent predecessor `schema-current` record after the four
v1 items. The first entry's predecessor commitment is SHA-256 of that extended
envelope; later entries still commit the exact preceding journal entry. A v2
transaction therefore requires a non-zero predecessor schema record. A legacy
zero-schema request remains entirely v1 rather than inventing zero extension
semantics.

The predecessor-inspection envelope remains kind `3`. Version 1 is unchanged:
its body/complete-record sizes are `177/193` bytes without rollback and
`257/273` bytes with rollback. Version 2 appends exactly the 32-byte selected
schema-record commitment, so its body/complete-record sizes are `209/225` and
`289/305` bytes respectively. Every other size/version combination rejects.

Both schema-record commitments are fixed before state 1 from the validated
`Plan` result and remain identical in every v2 entry. The predecessor commitment
is the record selected at initial inspection; the candidate commitment is the
deterministic record that would be selected at commit. Physical preparation is
proved separately: v2 state 3 uses `adapter-success` only after the exact
`SchemaWork` Plan/Prepare-or-preserve/Inspect sequence and code staging all
succeed. States 1-2 use `adapter-not-called`; states 4-12 retain their accepted
WorkControl, SelfTest, rollback, and commit mappings. A v1 state 3 remains
`adapter-not-called`.

The version-aware decoder accepts one complete canonical v1 chain or one
complete canonical v2 chain and rejects any mixture. V1 bytes are decoded under
the unchanged v1 rules and never synthesized into v2. A committed v1
transaction remains idempotent without a `SchemaWork` call or schema record.

The implementation-authorizing commit must amend these authoritative artifacts
together: `stage-7-s7.2-transaction-format-proposal.md` (Interface, manifest,
kind-3, journal-v2, kind-5 and R25-R34 bytes),
`stage-7-s7.2-task-contracts.md` (S7.2-06 criteria, scope and dependencies),
this brief, and `m3-s7.2-06-c7-vector.md`. If production adds or changes a
package/import, `package-map.md` and `dependencies.md` are amended in that
same commit. No brief alone authorizes a persisted-format change.

### D6 — exact operation and atomic commit order

For a new COW transaction, under the update-root lock:

1. build the same pure bounded inventory and recovery plan used by `Recover`;
   execute exact R28/R29 normalization before any Adapter call, reinspect once,
   and reject every unknown object, second temp, or contradictory fact;
2. validate the accepted Decision, exact plan, manifest-v2 candidate, and
   initialized `schema-current` without mutation;
3. match an identical committed request from complete owned records, return its
   reconstructed terminal Result without mutation or any Adapter call, and
   leave the runtime owner's separate readiness check responsible for detecting
   later foreign deletion;
4. for COW only, call `SchemaWork.Plan` once and validate the returned
   deterministic successor descriptor; schema-aware `no-op-v1` preserves the
   exact predecessor descriptor and proceeds directly to the bounded
   `Inspect` call in step 7;
5. include its exact bytes, entries, filesystem objects, schema record/temp,
   journal v2 bytes, and cleanup reserve in S7.2-03 resource admission. The
   update-root charge is exactly
   `round(candidate length, unit) + round(manifest-v2 length, unit) +
   9*round(203, unit) + round(successor-current length, unit) + round(176, unit)`
   for COW; the state-9 temp is one of the nine journal objects and the final
   term is its schema-current temp. The admitted update-root object lower bound
   is 16. For schema-aware no-op the exact charge is
   `round(candidate length, unit) + round(manifest-v2 length, unit) +
   9*round(203, unit) + round(successor-current length, unit)` and the admitted
   update-root object lower bound is 15: it omits only the schema-current temp.
   These counts
   cover only update-root objects; bounded foreign capacity belongs to
   `SchemaWork.Plan/Prepare`;
6. append journal-v2 states 1 and 2 through the accepted release/artifact
   verification path before the first foreign mutation;
7. stage the candidate code; call `Prepare` once for COW (not for schema-aware
   no-op), call `Inspect` on the exact candidate or preserved selection, require
   complete readability, and only then append state 3 `adapter-success`;
8. continue rollback reservation, stop, drain, and code activation using journal
   v2 while `schema-current` still selects the predecessor;
9. supply the exact candidate `SchemaSelection` to `SelfTest`; normal networking
   remains stopped;
10. after state 8 `adapter-success`, build and durably close the exact state-9
   journal temp and, for COW only, the exact schema-current sibling temp;
11. atomically replace and durably acknowledge `schema-current`; this is the
   commit linearization point and the only schema-selection change; then
12. publish the prewritten state-9 entry and sync its journal directory.

A schema-aware no-op skips step 11 because predecessor and candidate schema
records are byte-identical; its state-9 publication is the commit linearization
point and it never creates a schema-current temp or rewrites `schema-current`.
It still uses the exact prewritten state-9 journal temp, so R29 applies to both
schema-aware plans.

`Plan` and `Prepare` are therefore COW-only calls. Schema-aware no-op performs
only the exact preserved-selection `Inspect`; legacy zero-schema `no-op-v1`
performs none of the schema Adapter calls.

A crash after `Prepare` cannot be an unowned foreign residue: states 1-2 already
identify the exact transaction and both schema commitments. `Recover` does not
touch the foreign root, but a later identical `Apply` reinspects the prefix and
may call only the exact `Inspect`/`Discard` continuation. A preparation failure
uses the shared bounded cleanup for code staging and the exact planned foreign
candidate before returning; every cleanup error is observed.

The code `current` record changed earlier at state 7 and never claims schema
selection. Before step 11 old code remains the rollback and old schema remains
selected; candidate code is self-tested only against the prepared candidate
descriptor. After step 11 candidate code and candidate schema are selected. No
operation selects both by one ambiguous record.

The state-9 temp name is exactly `09-committed.entry.tmp` for a COW success.
It is written publish-new and cannot coexist with a final state-9 entry. Before
schema-current replacement, recovery removes any exact direct regular
single-link subset of these two unselected temp names, including a bounded
partial write, and returns state 8. After replacement, the complete state-9
temp and its exact commitments authorize
recovery to publish the already-written state-9 bytes; it does not reconstruct
elapsed time, resample a deadline, call an Adapter, or guess from a directory.

### D7 — failure, rollback, and bounded Result table

Dynamic Adapter/OS text is returned only in the error tree and is never
persisted or copied into `Result`.

| First observation | Outcome / state | Exact selected schema | Fixed safe notice |
|---|---|---|---|
| no-op or complete COW success | `committed/committed` | preserved / candidate | `update committed` |
| `Plan` says source is unsupported or cannot produce the exact plan | `release-incompatible/release-accepted` | predecessor | `update schema incompatible` |
| schema-aware no-op `Inspect` cannot prove the exact preserved selection | `release-incompatible/release-accepted` | predecessor | `update schema incompatible` |
| planned bytes/entries or admitted resources exceed a bound | `resource-denied/release-accepted` | predecessor | `update resources unavailable` |
| COW write, flush, publication, reopen, or complete validation fails after states 1-2 | `staging-failed/artifact-verified` | predecessor | `update schema staging failed` |
| Adapter returns a malformed/mismatched descriptor, selected source changes, or records contradict | `transaction-invalid/transaction-invalid` | no claim | `update transaction invalid` |
| schema-current temp/publication fails and complete predecessor remains selected | `schema-commit-incomplete/self-testing` | predecessor | `update schema commit incomplete` |
| exact successor schema-current is selected and exact state-9 temp exists | normalize to `committed/committed` | candidate | `update committed` |
| any cleanup/Discard operation fails or exceeds the continuation | `cleanup-incomplete/<last coherent state>` | physically inspected selection | `update cleanup incomplete` |

The two newly introduced public Outcome/state pairs are exactly
`release-incompatible/release-accepted` and
`schema-commit-incomplete/self-testing`. All other pairs in the table are
inherited from accepted earlier slices.

This slice adds exactly three bounded notices: `update schema incompatible`,
`update schema staging failed`, and `update schema commit incomplete`.
`update resources unavailable` is reused unchanged from S7.2-03. All accepted
S7.2-01/S7.2-05 notices remain unchanged; no dynamic Adapter or OS text enters
the bounded vocabulary. `schema-commit-incomplete` is deliberately distinct
from S7.2-03 code-artifact staging failure and S7.2-09 evidence failure.
When the complete predecessor remains selected, a later identical `Apply` or
`Recover` may retry only the exact R28 cleanup or R29 publication path; it
does not restage code, resample deadlines, or call a foreign Adapter during
`Recover`.

A forward self-test failure enters the accepted S7.2-05 rollback path while the
predecessor schema is still selected. Rollback schema compatibility passes only
when the exact predecessor `schema-current`, retained code, and their journal
commitments remain coherent and the schema owner reports the predecessor fully
readable. Otherwise rollback is `rollback-refused/repair-required` and retained
code is not started.

This is the schema-aware specialization of inherited row R17: when state 8
records `adapter-failed`, the exact predecessor schema is still selected and
must pass the one predecessor `Inspect` before the retained-code start Adapter
may run.

Each invocation performs at most two `Inspect` calls total: exactly one initial
candidate-or-preserved-selection inspection, plus at most one predecessor
inspection after a forward self-test failure. The predecessor inspection is
intentionally non-durable and is
repeated on a later explicit attempt. Its failure yields
`rollback-refused/repair-required`, appends state 12 with
`adapter-not-called`, joins the original self-test error, and never calls the
retained-code start Adapter.

After safe predecessor code selection, `Discard` removes only the unselected COW
candidate. Success may append `rolled-back`; failure returns
`cleanup-incomplete/rollback-pending` with predecessor code/schema selected and
normal networking stopped. A later identical `Apply` may retry only this exact
Discard and terminal acknowledgement. Rollback never selects, copies, or
reconstructs schema, and never changes Authority, release, Network Epoch,
Namespace, freshness, generation, exposure, Credential, Grant, or watermark
state.

### D8 — physical postconditions

| Durable condition | Code current | Schema current | Foreign COW candidate | Normal networking |
|---|---|---|---|---|
| pre-stop or schema staging failure | predecessor | predecessor | absent after successful Discard | unchanged |
| activated/self-testing | candidate; predecessor rollback | predecessor | complete, immutable, unselected | stopped |
| committed | candidate; predecessor rollback | candidate | selected and retained | may be started by runtime owner |
| rollback-pending before code rollback | candidate; predecessor rollback | predecessor | unselected | stopped |
| rolled-back | predecessor; rollback absent | predecessor | absent | stopped during operation |
| rollback refused | candidate; predecessor rollback | predecessor | preserved for inspection | stopped |
| repair-required after retained start failure | predecessor; rollback absent | predecessor | absent after successful cleanup | stopped |
| cleanup-incomplete | exact last coherent code/schema selections | never guessed | exact declared residue only | stopped |

No row stores schema content below `<updateRoot>`, mutates a selected schema
generation, makes a foreign COW generation a code rollback payload, or makes
presence alone authoritative.

### D9 — global R25-R34 interruption extension

S7.2-02 freezes R00-R14 and S7.2-05 freezes R15-R24. This brief reserves the
next exact global range R25-R34. No later task may renumber or reinterpret these
rows; the authoritative format amendment publishes one combined table.

Every row has a direct regular permanent lock, a canonical journal prefix, and
the exact schema commitments from journal v2. Recover validates only the
transaction-owned records and never claims a new foreign-root observation.

| ID | Last journal / physical facts | Required one-pass recovery |
|---|---|---|
| R25 | no transaction evidence; predecessor schema selected; no update-root temp | return `recovered/idle`; Recover neither enumerates nor mutates foreign residue |
| R26 | state 1-7 prefix; predecessor schema selected | preserve exact prefix/selection and return `recovered/<last state>` |
| R27 | state 8 success; predecessor schema selected; no commit temps | preserve and return `recovered/self-testing` |
| R28 | R27 plus one or both exact bounded direct regular single-link temp names, complete or interrupted; predecessor still selected; facts do not satisfy R29 | remove only the observed temp subset under cleanup continuation; normalize to R27 |
| R29 | state 8 success and exact complete prewritten state-9 temp bound to the selected schema record; either COW candidate schema-current is selected, or schema-aware no-op has byte-identical predecessor/candidate selection | publish that exact temp, sync journal, return committed |
| R30 | state 9; candidate schema-current selected | return unchanged committed Result |
| R31 | distinct COW candidate schema-current selected but state-9 temp missing, malformed, or inconsistent | `transaction-invalid`, no mutation and no Adapter call |
| R32 | state 9 with the distinct COW predecessor schema selected, or any pre-state-8 prefix with distinct candidate selected | `transaction-invalid`, no mutation and no Adapter call |
| R33 | state 10 rollback-pending; predecessor schema selected; foreign candidate disposition unknown | preserve and return accepted rollback-pending recovery; only identical Apply with Adapter may continue/discard |
| R34 | state 11 or 12 with schema selection inconsistent with D8 | `transaction-invalid`; otherwise return the accepted S7.2-05 terminal result unchanged |

Recover never opens `<schemaRoot>` itself and never calls `Plan`, `Prepare`,
`Inspect`, or `Discard`. It never deletes a foreign generation, guesses Adapter
completion, or treats foreign directory presence as evidence. Exact
update-root temps are its only additional cleanup allowlist. A partial/mixed selection record, wrong
predecessor, mixed journal version, unknown object, or extra temp is invalid
and preserved.

Terminal authority is either a complete state-9 journal entry or the exact
complete prewritten state-9 temp bound to the selected schema record. The
`schema-current` replacement is the COW selection linearization point, but
presence of that record alone never proves a committed transaction; R29 is the
only permitted roll-forward.

R29 also covers the same-invocation atomic-replace ambiguity: if the schema
replacement call reports an error but the subsequent owned-record observation
proves that the exact candidate selection was in fact durably installed, Apply
may publish only the already complete, commitment-matching state-9 temp. Any
other observation follows R28 or R31; it never retries the replacement blindly.

The limitation is explicit: after a crash, Recover can prove that the candidate
was completely inspected before the atomic schema-selection record changed,
and that the exact prewritten commit entry binds that selection. It cannot prove
that an Owner or foreign schema Module did not delete content afterward. The
idempotent Apply of an already committed transaction returns the preserved
terminal Result and does not reopen foreign state or append another state. The
runtime schema owner performs its own bounded `Inspect`/readiness check before
networking starts. If foreign content disappeared after commit, networking
remains stopped and an explicit repair operation outside the completed
transaction is required. `Recover` and idempotent replay never append rollback
or repair states after `committed`.

Retention and pruning of foreign schema generations belong to the future schema
owner, not Update Transaction. S7.2-08's no-growth claim covers only the update
root and cannot be cited as a bound on the D4 fixture root. This slice retains
the selected predecessor/candidate facts needed for its transaction but makes
no production retention-policy claim for foreign content.
