# Reference Invariants

## 1. Назначение

Этот документ фиксирует несущие инварианты `aim-core` как референс-реализации.

Его задача не в том, чтобы объявить `aim-core` канонической архитектурой нового
продукта. Его задача в том, чтобы зафиксировать:

- что в `aim-core` является системообразующим;
- что нельзя потерять при разработке нового продукта;
- что может быть переписано только при наличии полноценного эквивалента;
- где заканчивается архитектурный дефект legacy и где начинается несущий механизм системы.

Этот документ обязателен для всех последующих архитектурных и кодовых решений.

## 2. Базовое Правило

`aim-core` нельзя копировать как архитектурную форму.

Но `aim-core` нельзя и читать только как набор дефектов.

Если в `aim-core` есть механизм, без которого система перестаёт существовать как
рабочая сеть, этот механизм считается reference invariant и не может быть:

- опущен;
- заменён эвристикой;
- размыт в local-only simplification;
- заменён другой технологией без доказанного эквивалента по роли.

## 3. Что Считается Reference Invariant

Reference invariant - это свойство или механизм, который в `aim-core` выполняет
несущую системную роль.

Он определяется не тем, “красивый” ли он архитектурно, а тем:

- держит ли он систему живой;
- обеспечивает ли он существование сети как сети;
- зависят ли от него discovery, messaging, service exposure и runtime behavior;
- распадается ли продукт без него на локальные заглушки и ручные сценарии.

## 4. Главные Несущие Инварианты `aim-core`

### 4.1 У системы есть одна реальная сетевая основа

В `aim-core` сеть существует не как идея и не как набор строковых endpoint hints.

У системы есть конкретный сетевой substrate, через который становятся возможны:

- участие узла в общей сети;
- peer connectivity;
- transport exchange;
- discovery publication и intake;
- messaging;
- часть operational runtime behavior.

Следствие:

- новый продукт не может считаться сетью, если у него нет одной реальной canonical network foundation;
- transport layer не может быть “временно символическим” в финальной форме продукта.

### 4.2 `waku` в `aim-core` является не деталью, а несущей основой сети

В `aim-core` именно `waku` играет роль главного network substrate.

Даже если legacy допускает другие transport modes, рабочая форма сети в
референсе опирается именно на `waku` как на системный механизм.

Это означает:

- `waku` нельзя трактовать как случайный adapter;
- его нельзя считать просто одним из вариантов transport implementation;
- если новый продукт не использует `waku`, он обязан иметь доказанный эквивалент по системной роли;
- отсутствие такого эквивалента означает потерю несущего инварианта референса.

### 4.3 Сеть должна быть operational, а не local-only

В референсе сеть предполагает:

- реальное участие узла в общей среде;
- не только локальное хранение records;
- не только ручной import/export;
- не только local API без network life.

Следствие:

- local-first каркас может быть переходным шагом;
- но продукт не может считаться собранным, пока discovery, communication и publication не живут на реальной сети.

### 4.4 Discovery - часть живой сети, а не локальный каталог

В `aim-core` discovery связано с сетевым substrate и сетевой жизнью узла.

Это означает:

- discovery нельзя редуцировать до локального реестра записей;
- import/export записью не является полноценной заменой network-fed discovery;
- service discovery должно быть связано с реальной reachability и сетевым существованием узла.

### 4.5 Trust влияет на usable outcomes, а не существует как отдельная справка

В референсе trust не является декоративной информацией.

Trust должен участвовать в решениях:

- можно ли использовать запись;
- можно ли использовать peer;
- можно ли строить route;
- можно ли считать service usable.

Следствие:

- trust model не может остаться только explainability-слоем;
- trust должен менять runtime behavior продукта.

### 4.6 Service publication должно быть связано с runtime reality

Опубликованный service не может считаться реальным только потому, что его кто-то
декларировал в конфиге или записи.

В референсе service exposure связано с живым runtime и transport presence.

Следствие:

- hosted service publication должно зависеть от runtime truth;
- service publication без реального runtime и без сетевой основы - ложное поведение.

### 4.7 Узел - это управляемая runtime-система, а не только сетевой клиент

В референсе узел является не только участником сети, но и локальной runtime-системой:

- с identity;
- с local control surface;
- с lifecycle;
- с diagnostics;
- с hosted/runtime behavior.

Следствие:

- новый продукт не может быть только сетевым агентом;
- он обязан оставаться полноценным управляемым узлом.

## 5. Что Не Является Обязательным Invariant

Следующие вещи в `aim-core` не обязаны сохраняться как форма:

- умножение слоёв `domain/usecase/service/contracts/sdk`;
- runtime facade как центральный хозяин архитектуры;
- parallel contract systems;
- legacy package topology;
- прежний repo shape;
- старые service/API surfaces как каноническая форма нового продукта.

То есть:

- инварианты референса касаются несущих механизмов и обязательного поведения;
- они не обязывают копировать legacy-структуру.

## 6. Правило Замены Несущего Механизма

Если в новой системе заменяется reference invariant, допустима только такая замена,
которая проходит equivalence test по роли.

Для замены нужно доказать:

- что новый механизм обеспечивает ту же системную функцию;
- что discovery, messaging, service publication и network participation не теряют опору;
- что продукт без старого механизма не распадается на local-only simplifications;
- что оператор и runtime по-прежнему получают объяснимую систему.

Если это не доказано, замена запрещена.

## 7. Практические Следствия Для Разработки

Из этого документа следуют жёсткие правила:

- нельзя строить новую сеть как набор локальных эвристик;
- нельзя заменять `waku` “каким-то transport package” без доказанной эквивалентности;
- нельзя считать транспорт, discovery и service publication второстепенными деталями;
- нельзя делать roadmap и domain map, не зафиксировав canonical network foundation;
- нельзя объявлять root-реализацию “правильным направлением”, пока не доказано сохранение reference invariants.

## 8. Вопросы, На Которые Дальше Должны Ответить Следующие Документы

После этого документа новая документация обязана ответить на вопросы:
- как устроены runtime flows вокруг identity, discovery, messaging и service publication;
- как эти инварианты отражаются в new system boundaries;
- какие части текущего root-кода сохраняют эти инварианты, а какие нарушают их.

Вопрос canonical network foundation уже должен считаться закрытым отдельным
решением и не может оставаться открытым во время разработки.
