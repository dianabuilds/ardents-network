# Development Contract

## 1. Назначение

Этот документ фиксирует обязательный режим разработки Ardents.

Он нужен затем, чтобы:

- не допускать prototype-first development;
- не возвращаться к fake implementations и временным foundation;
- сохранять фокус на продукте, а не на промежуточных каркасах;
- не терять системные решения при длинной разработке и сжатии контекста.

## 2. Базовый Принцип

Ardents разрабатывается не через цепочку:

- прототип;
- временная реализация;
- "потом заменим";
- "потом доведём до продукта".

Ardents разрабатывается только через product-grade domain implementation.

Это означает:

- домен нельзя реализовывать как временный скелет;
- домен нельзя завершать metadata-only substitute;
- домен нельзя считать готовым, если его ключевые свойства отложены "на потом";
- критические плоскости нельзя строить на fake foundation.

## 3. Что Запрещено

Запрещено:

- делать fake executor как нормальный путь продукта;
- делать local-only imitation сетевого поведения в качестве основной реализации;
- делать metadata registry вместо реального data substrate;
- вводить временный transport core;
- вводить "упрощённую пока что" publication model, если она ломает product truth;
- писать код с расчётом, что обязательные свойства домена будут добавлены позже.

## 4. Что Разрешено

Разрешено разбивать работу на slices, но каждый slice обязан быть:

- вертикальным;
- product-meaningful;
- runtime-real;
- объяснимым;
- тестируемым;
- совместимым с целевой формой домена.

Иными словами:

- разрешено делать часть домена;
- запрещено делать ложную форму домена.

## 5. Правило Начала Работы Над Доменом

Домен можно начинать в коде только если уже известно:

- за что домен отвечает;
- чем он владеет;
- что он не должен делать;
- какие свойства обязательны для его продуктовой формы;
- как проверить, что он реализован не как прототип, а как часть продукта.

Если это не ясно, сначала обновляются документы, а не пишется код.

## 6. Completion Gate Для Любого Slice

Slice нельзя считать завершённым, если одновременно не выполнены условия:

- код меняет реальное runtime behavior;
- обязательные свойства соответствующего домена не нарушены;
- не введён временный foundation вместо product-grade решения;
- результат объясним через diagnostics и/или local control surface;
- есть тесты на success path и хотя бы один failure/degraded path.

## 7. Обязательная Проверка Перед Кодом

Перед любым существенным изменением нужно проверить:

- `system-concept.md`
- `system-frame.md`
- `system-properties.md`
- `canonical-network-foundation.md`
- `engineering-constraints.md`
- доменный документ, к которому относится изменение

Если изменение противоречит хотя бы одному из них, сначала меняются документы.

## 8. Нарушение Контракта

Нарушением считается:

- добавление временной реализации в critical plane;
- реализация домена в урезанной ложной форме;
- обход canonical network foundation;
- самописный substrate там, где он запрещён;
- код, который выглядит как foundation, но не закрывает обязательные свойства домена.
