# Data Substrate Requirements

## 0. Role In Docs Set

This is a supporting deep-dive for retention, availability, transfer, and
privacy-sensitive data behavior inside `Data Substrate`.

It complements, but does not replace:

- `system-frame.md`
- `system-properties.md`
- `docs/domains/data-substrate.md`
- `persistent-state-security.md`

If this document conflicts with the core or domain documents, the core and
domain documents remain authoritative and this file must be realigned.

## 1. Назначение

`Data Substrate` - домен удержания, хранения, доставки и повторной отдачи сообщений,
вложений, payload-данных и blob-данных в сети Ardents.

Этот домен существует для того, чтобы:

- данные не зависели от одного центрального сервера;
- данные не исчезали сразу после ухода отправителя офлайн;
- участники чата могли хранить историю и файлы локально;
- другие узлы могли временно удерживать зашифрованные копии;
- уже скачавшие участники могли становиться дополнительными источниками;
- доступность и скорость отдачи росли при наличии нескольких копий.

Это не "storage вообще" и не только локальный cache. Это продуктовый слой
распределённого удержания и выдачи данных.

## 2. Что Входит В Домен

Домен владеет:

- `Message Payload`
- `Attachment`
- `Blob`
- `Manifest`
- локальной информацией о хранении, удержании, источниках и сроках жизни копий

### 2.1 Blob

`Blob` - минимальная единица бинарного содержимого.

Примеры:

- файл;
- часть большого файла;
- сериализованный payload;
- зашифрованный фрагмент данных.

Canonical identity contract:

- payload-backed blob ID must match the content-derived CID; local store, relay retention, and fetch acceptance cannot bind payload under a different logical ID.
- metadata-only blob may exist before payload is available, but once CID is known the ID/CID pair must remain canonical and drift-free.
- fetch request acceptance must preserve the mapping between requested blob ID and accepted content identity; otherwise the response is not authoritative truth.

### 2.2 Manifest

`Manifest` - описание состава данных и правил доступа к связанным blob-данным.

Минимально manifest должен позволять понять:

- из каких blob состоят данные;
- в каком порядке или с какими ролями они связаны;
- какие retention и access свойства у этих данных;
- какие данные нужны клиенту, чтобы запросить содержимое.

## 3. Базовые Сценарии

Система обязана поддерживать следующие сценарии.

### 3.1 Локальное хранение участником

Участник чата может хранить у себя:

- историю сообщений;
- вложения;
- файлы и blob-данные, относящиеся к чатам, в которых он участвует.

### 3.2 Временное удержание relay-узлами

Узел может временно удерживать чужие данные, не являясь их владельцем.

Типичные режимы:

- `24h`
- `7d`
- иные сроки, заданные конфигурацией и политикой

### 3.3 Доступность после ухода отправителя

Если отправитель офлайн, данные должны оставаться доступными, если существует хотя бы одна
доступная копия:

- у получателя;
- у relay-узла;
- у другого участника, который уже скачал данные.

### 3.4 Повторная отдача

Участник, уже скачавший данные, может стать источником их дальнейшей раздачи.

Это нужно для:

- сохранения доступности;
- ускорения загрузки;
- распределения нагрузки между несколькими источниками.

## 4. Обязательная Модель Доступа

### 4.1 Шифрование

Чужие данные, удерживаемые узлом, должны храниться в виде, непригодном для чтения владельцем узла.

Следствия:

- удержание не даёт права чтения;
- наличие локальной копии не означает доступ к plaintext;
- расшифровка должна зависеть от прав участника, а не от факта хранения данных.

### 4.2 Роли

Для каждого набора данных и blob система должна различать:

- владельца данных;
- участника с правом чтения;
- узел, временно удерживающий копию;
- узел, доступный как источник раздачи;
- узел, у которого копия pinned локально.

Эти роли могут совпадать, но не должны считаться тождественными.

### 4.3 Право на повторную отдачу

Повторная отдача должна зависеть от:

- локальной конфигурации узла;
- применимой политики;
- факта наличия корректной локальной копии;
- режима доступа к конкретному типу данных.

## 5. Модель Жизненного Цикла

Каждый blob и каждая удерживаемая единица данных должны проходить различимые состояния.

Минимальная модель:

- `announced`
- `available-local`
- `available-remote`
- `retained-temporary`
- `pinned`
- `expired`
- `deleted`

### 5.1 Смысл состояний

- `announced`: данные известны системе, но локальной копии ещё нет
- `available-local`: локальная копия есть и может быть использована
- `available-remote`: локальной копии нет, но есть известные удалённые источники
- `retained-temporary`: локальная копия удерживается ограниченное время
- `pinned`: локальная копия удерживается явно и не подлежит обычной очистке
- `expired`: срок удержания истёк, копия подлежит удалению
- `deleted`: локальная копия удалена и более не считается доступной локально

Observed state должен храниться отдельно от желания клиента или приложения.

These values describe retention and payload state of one known copy. They are
not aggregate object-availability states and do not establish a replication
guarantee. Aggregate `target-satisfied`, `best-effort`, `degraded`,
`unavailable`, and `lost` semantics are defined in
`docs/data-availability-replication-semantics.md`.

## 6. Удержание И Репликация

### 6.1 Удержание

Система должна уметь удерживать:

- собственные данные пользователя;
- данные чатов, в которых он участвует;
- чужие зашифрованные данные в режиме временного relay retention.

### 6.2 Репликация

Полноценная "вечная" глобальная репликация не является обязательной по умолчанию.

Но система обязана поддерживать:

- наличие нескольких независимых копий;
- использование уже скачавших участников как дополнительных источников;
- рост доступности при росте числа копий.

### 6.3 Источники

Для каждого blob или набора данных система должна уметь различать:

- локальный источник;
- исходного отправителя;
- другого участника чата;
- relay-узел с временной копией;
- произвольный удалённый узел, у которого подтверждена доступная копия.

## 7. Что Должно Быть Конфигурируемым

Как минимум должны настраиваться:

- включено ли удержание чужих данных;
- максимальный размер локального хранилища;
- квота под временные чужие копии;
- срок удержания по умолчанию;
- срок удержания по типу данных;
- разрешение на повторную отдачу;
- разрешение на pin;
- лимиты cache;
- приоритет собственных данных над временными копиями;
- правила очистки expired данных.

Конфигурация не должна быть произвольной: допустимые режимы ограничиваются политикой продукта.

## 8. Границы Домена

### 8.1 Data Substrate Делает

- хранит metadata о payload, attachment и blob-данных;
- хранит локальные копии blob-данных;
- отслеживает observed availability;
- отслеживает retention и expiry;
- знает локальные и удалённые источники;
- отдаёт данные в сеть и локальным клиентам;
- участвует в повторной раздаче;
- предоставляет explainable status для оператора и API.

### 8.2 Data Substrate Не Делает

- не определяет transport protocol сам по себе;
- не заменяет messaging domain;
- не решает trust policy самостоятельно;
- не является generic filesystem abstraction;
- не сводится к metadata registry без реального удержания данных.

## 9. Связь С Другими Доменами

### 9.1 С Network / Messaging

`Data Substrate` использует сетевую плоскость для:

- объявления доступности данных;
- поиска источников;
- загрузки и повторной раздачи.

### 9.2 С Trust

`Trust` влияет на:

- использование удалённых источников;
- пригодность копии к загрузке;
- допустимость удержания и повторной отдачи в отдельных режимах.

### 9.3 С Policy

`Policy` влияет на:

- что можно хранить;
- сколько можно хранить;
- как долго можно удерживать;
- можно ли участвовать в повторной раздаче;
- какие данные можно pin.

### 9.4 С Diagnostics

`Diagnostics` обязаны объяснять:

- почему данные доступны или недоступны;
- почему копия удерживается или удаляется;
- почему загрузка не удалась;
- какие ограничения наложены политикой или конфигурацией.

## 10. Видимость Для Оператора

Оператор узла должен иметь возможность увидеть:

- общий объём локальных данных;
- объём собственных данных;
- объём чужих временных копий;
- pinned данные;
- данные, ожидающие expiry;
- данные, доступные для повторной отдачи;
- причины недоступности payload, attachment или blob;
- ограничения, применённые конфигурацией и политикой.

## 11. Минимальные Критерии Реализации

Домен нельзя считать реализованным, пока одновременно не выполняются все условия:

- данные можно сохранить локально как payload/attachment и blob;
- данные можно зашифрованно удерживать на чужом узле без доступа хранителя к plaintext;
- данные остаются доступными после ухода отправителя, если есть другая копия;
- уже скачавший участник может стать источником повторной отдачи;
- удержание ограничивается временем и/или политикой;
- доступность и недоступность данных объяснимы через API и diagnostics;
- оператор может управлять retention и storage limits через конфигурацию.

## 12. Что Этот Документ Намеренно Не Фиксирует

Этот документ не выбирает:

- конкретную технологию реализации;
- конкретный протокол передачи;
- конкретную криптографическую схему;
- transport-specific segmentation below the canonical Data Substrate chunk;
- конкретный внешний storage engine.

The selected `v1` replication, lease, availability, object/manifest, and
canonical 64 KiB chunking contract is defined in
`docs/data-availability-replication-semantics.md`.

Он задаёт только тот объём требований, который должен быть достаточен для проектирования и реализации домена без дополнительных специальных документов по нему.
