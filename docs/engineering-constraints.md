# Engineering Constraints

## 1. Назначение

Этот документ фиксирует обязательные ограничения на реализацию Ardents.

Его задача:

- не дать разработке снова уйти в произвольную архитектуру;
- не дать заменить зрелые зависимости самописными реализациями без решения;
- зафиксировать требования к безопасности зависимостей и runtime;
- сделать отклонение от курса явным нарушением, а не "вариантом реализации".

## 2. Обязательные Ограничения На Реализацию

### 2.1 Нельзя Писать Свой Substrate С Нуля

Для `v1` запрещено писать с нуля:

- network substrate;
- messaging substrate;
- database engine;
- wire protocol framework;
- observability substrate;
- crypto primitives;
- content-addressing primitives.

Собственная реализация допустима только для product semantics, а не для базовой инфраструктуры.

### 2.2 Нельзя Обходить Canonical Network Foundation

Если для `v1` canonical network foundation зафиксирован как `Waku`, то запрещено:

- строить альтернативный основной transport path;
- делать новый neutral transport core "на всякий случай";
- писать network plane так, будто substrate можно выбрать позже;
- подменять реальную сеть локальными эвристиками и endpoint scoring.

### 2.3 Нельзя Тихо Подменять Зависимость

Любая замена несущей зависимости допустима только если:

- есть отдельное архитектурное решение;
- есть доказательство эквивалентности по роли;
- обновлены документы, которые от этого зависят;
- есть объяснение, что именно выигрывается и что не теряется.

Без этого замена запрещена.

### 2.4 Нельзя Делать "Временную" Самописную Реализацию В Critical Plane

Запрещено вводить "временные" реализации в critical plane, если они:

- выглядят как реальный foundation;
- начинают обрастать зависимостями;
- мешают последующему переходу на правильный substrate;
- создают ложное ощущение готовности продукта.

Если временный stub всё же нужен, он должен быть явно обозначен как non-product path.

## 3. Dependency Policy

### 3.1 Общие Правила

Каждая прямая зависимость должна быть:

- осознанной;
- необходимой;
- связанной с одним из зафиксированных доменов или системных требований;
- поддерживаемой и живой;
- приемлемой по security posture.

### 3.2 Что Обязательно Проверять Для Зависимости

Перед принятием зависимости должны быть проверены:

- активность проекта;
- понятный ownership / maintainership;
- совместимость лицензии;
- наличие release process;
- наличие известных критических уязвимостей;
- отсутствие заброшенного состояния;
- реальная применимость к нашей задаче.

### 3.3 Что Считать Неприемлемой Зависимостью

Неприемлемой считается зависимость, если:

- у неё есть известные критические или high severity уязвимости без внятного remediation path;
- проект заброшен;
- проект не используется как production-grade foundation;
- зависимость тянет чрезмерный объём лишнего substrate без необходимости;
- она решает не ту задачу, которая нам реально нужна.

## 4. Security Requirements For Dependencies

### 4.1 Обязательная Проверка Уязвимостей

Для всех прямых зависимостей и критичных transitives должны выполняться:

- проверка известных уязвимостей;
- повторная проверка при обновлениях;
- фиксация риска, если безопасная версия ещё недоступна.

### 4.2 Нельзя Молчаливо Оставлять Известно Уязвимую Версию

Если зависимость имеет известную значимую уязвимость, запрещено:

- игнорировать это;
- оставлять версию без решения;
- продолжать разработку так, будто проблема отсутствует.

Нужно либо:

- обновить зависимость;
- зафиксировать compensating control;
- зафиксировать residual risk в `docs/security-exceptions.md`;
- отказаться от зависимости;
- или заблокировать соответствующий slice как небезопасный.

Если выбран compensating-control path, он допустим только при одновременном выполнении всех условий:

- уменьшена reachable surface;
- ограничен blast radius;
- зафиксирован operational detection path;
- зафиксирован upgrade trigger;
- решение явно отражено в `docs/security-exceptions.md`.

### 4.3 Security Выше Удобства Интеграции

Нельзя выбирать зависимость только потому, что с ней "быстрее подключиться",
если её security posture делает продукт рискованным.

## 5. Runtime Security Requirements

### 5.1 Шифрование И Изоляция

Если домен требует encrypted retention, запрещено реализовывать его так, чтобы:

- владелец relay-узла имел доступ к plaintext;
- ключи были доступны по факту хранения данных;
- временное удержание означало владение содержимым.

### 5.2 Secrets И Key Material

Ключевой материал должен:

- храниться отдельно от обычных временных данных;
- не утекать в diagnostics, logs и API;
- не смешиваться с relay-retained payload data.

### 5.3 Diagnostics Не Должны Ломать Security Model

Diagnostics обязаны быть explainable, но не должны:

- раскрывать чувствительные payload data;
- раскрывать ключи;
- раскрывать секреты, достаточные для чтения чужих данных.

## 6. Контроль Фокуса Разработки

Перед началом любого нового slice разработка обязана проверить:

- не противоречит ли slice `system-concept.md`;
- не ломает ли slice `system-frame.md`;
- не обходит ли slice `canonical-network-foundation.md`;
- не игнорирует ли slice `reference-invariants.md`;
- не нарушает ли slice этот документ.

Если хотя бы один ответ неясен, slice нельзя считать готовым к реализации.

## 7. Что Считается Нарушением

Нарушением считается:

- новый самописный substrate в critical plane;
- неявная замена canonical foundation;
- добавление небезопасной зависимости без решения;
- игнорирование известных уязвимостей;
- реализация security-sensitive behavior без учёта требований домена;
- код, который противоречит зафиксированным системным решениям, но продолжает развиваться как будто это допустимо.
