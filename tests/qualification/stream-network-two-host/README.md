# Two-host installed stream qualification

`run-windows.ps1` owns one explicit installed #60 attempt across the declared
Publisher and User hosts. It installs the exact runner and worker candidates,
starts the Publisher first, completes the real offline admission-permission
handover, obtains the actual Target Link, installs the four-Reader plan with
that Link, completes all four handovers, and retains both invocation journals.
It then runs `verify-pair` against those unedited journals, terminal relay
counters and sixteen Route Node owner records on the installed Linux candidate.

Every preparation and attempt requires the full lowercase `SourceCommit` to
equal the clean checked-out HEAD. The attempt and input receipts retain it, and
the NET-14V verifier refuses evidence from different source commits.


`fixturecommand/qualification-network` creates the owner-private raw fixture input for one carrier/cell: twenty-three canonical State records and materializations (sixteen Route Nodes, five Endpoint participants and two Sources), Node and Source credentials, retained Reader/Publisher Entry roots, and a manifest that already matches those retained selections. Its seed is a fixture reproducibility input and derives private test keys, so the generated directory is secret test material and must remain outside the repository. The separate preparation command uses public product commands to initialize and accept the durable roots; generated bytes alone are not runtime acceptance.

Generate one private bundle outside the repository for every Carrier, cell and
profile. Use the same seed, start instant and host pair for the complete matrix.
Each cell owns distinct one-use Service, publication, token and local-role
roots. All cells and both Carriers share the same seed-bound hosting-period
root, so a new scenario or identity cannot reset the owner's provider
allowance. The selected TCP/TLS normal input also provisions a separate
NET-32 participant and Service generation, so the idle projection cannot reuse
a generation consumed by the stream workload. The fixture validity window is six hours and the
start instant must be aligned to a UTC hour so the closed issuer owns the same
six-hour window. The preparer refuses to start unless at least four hours remain.

prepare-windows.ps1 consumes the generated provisioning-inventory.json,
the four static Linux command binaries, exact provider-period bounds,
original provider units and quantities, and already-consumed byte floors. It uploads the private bundle, creates the
admission and Service authorities through terminal-confined custody, accepts all 23
State roots, initializes the closed issuer and six Service Instances, signs
and accepts the closed profile, and initializes the shared hosting owner on
each machine. It retains only public receipts and the signed profile in a new
external preparation directory. Preparation generates separate admission and
Service secrets. The reusable admission secret is retained only as a DPAPI
ciphertext bound to the current Windows account; the Service secret remains
in the preparation process. Both are delivered through an SSH pseudo-terminal
with echo disabled, never through process arguments, environment variables, or
evidence. Request commitments are computed from independently downloaded public
request files and supplied through the same terminal channel.
The script never infers provider period dates or consumed traffic.
The two plans must reference already provisioned current State, Service
Instance, role/token/publication roots and one existing provider hosting period.
The script neither creates authority nor resets those durable roots. The
authority inventory names an existing `ardents-custody` vault and its exact
public binding. The runner resolves the adjacent protected secret and can only
decrypt it under the Windows account that performed preparation.

The reader plan is an immutable template with an empty `Link` on each of its
four participants. The script fills all four with the one Publisher-emitted
Link before root installation. Plans must already select the same workload
profile, network condition and seed.

`NetworkManifest` is mandatory. The installed candidate verifies its exact raw
SHA-256, generator identity, ordered seed schedule, carrier, two directional
paths, twelve directional segments and six physical-link relays before either Endpoint starts. The
manifest must model the asymmetric 20/100 Mbit/s User edge and the exact
end-to-end delay, independent loss placement, jitter ceiling and failure
schedule for the selected condition. A plan seed absent from the frozen
schedule fails before the long run.

`RelayBinary` is the static Linux build of the repository's bounded `netem-relay`. The orchestrator requires the same immutable `golang@sha256:3c3e25a4da13fd0478eed2df1eb35a0e667094a7124d3993a6a1d30f71c17e79` relay image on both hosts and retains each local image identity. It starts the manifest's six relays in disposable
Docker namespaces, applies separate upstream/client `tc` classes, retains raw
qdisc/class/filter receipts, and removes every started container on success or
failure. Relay targets are literal IPv4 endpoints; DNS and host interfaces are
outside this controlled cell.


`NodeBinary` and `NodeInventory` are mandatory. The inventory has exactly sixteen
entries: twelve forwarding duties and one each for issuer, resolution, introduction
and data JOIN. It must include the five intermediate Node IDs in both manifest paths.
Each entry names `reader` or `publisher` placement and an existing canonical
Node plan. Every Node on the five-position data path binds the exact private
manifest relay target through `closed_listen_private_override`; all other Nodes
leave that field absent. The Service Interior forwarding plan also binds the
fourth physical relay's public endpoint through `carrier_relay_endpoint`. This
adapter changes only the socket address: State still owns the selected Node
identity, duty, Carrier, TLS key and peer authentication. Every plan must use
the same provider hosting root as its Endpoint owner. Before any relay or Node
starts, the installed candidate preflights the complete owner inventory,
accepted State/profile, live clock observation, Service Instance, publication
and token roots, fixed worker artifact, and actual hosting period. The
orchestrator then starts each real Node in a separate systemd cgroup,
waits for READY, enables systemd IP accounting, and records one-second
memory/CPU, per-process tx/rx, and Node hosting samples, then requires
WITHDRAWN and a clean exit. The pair verifier adds the colocated Node aggregate
to the Endpoint and worker owner measurement. The complete User owner is bounded
to 512 MiB RSS and 50% of one CPU; the complete Publisher owner is bounded to
1 GiB RSS and one CPU. Each Node unit also retains its one-CPU containment bound.
The pair verdict binds every Node's systemd counters and separately derives the five
data-path Node totals from adjacent directional relay classes. It refuses an incomplete
Node set.

`verify-net14v-windows.ps1` reuses one passed `net14ad` attempt as the normal
baseline for its matching `net14-recovery` attempt, then runs the candidate verifier
on the Publisher host, and retains the final episode, directional bitrate and
eight-MiB-addition verdict. It refuses mixed Carrier, profile, seed or runner
inputs before upload.

For `net14-recovery`, the runner starts the manifest's fixed failure schedule
after measured stream progress begins. Faults run in bounded transient units,
may overlap, restore the exact declared netem class, and retain actual start and
stop times. A missing, late or unclean recovery scheduler fails the attempt.
If the workload fails after relays start, the runner captures their last sampled
class counters and recovery journals before cleanup. The candidate verifier then
requires a conservative eight-MiB absolute bound for every completed failure
window; missing samples or an incomplete schedule remain a failed verdict.
This runner records an installed normal/impaired/recovery attempt. A controlled
network manifest and its separately isolated relay are still required to claim
NET-14AD or NET-14V; the script never changes a production host interface or
labels an unshaped run as either cell. Evidence output must be a new directory
outside the repository. Permission bytes and vault secrets are never retained
there.

Run from PowerShell 7 (`pwsh`) with the two host addresses, private-key path,
candidate binaries, both plan paths, authority inventory and a fresh external
evidence directory. The outer attempt is limited to 22 minutes. Any missing
terminal record, failed service, incomplete cleanup, changed artifact, custody
failure or pair mismatch fails and remains in the evidence directory.

## Batch smoke and acceptance matrix

`run-matrix-windows.ps1` is the only outer command for the complete candidate.
It first validates all eight Carrier, direction and condition cells and the
NET-32 input, writes every validation failure to `matrix-report.jsonl`, and
performs no remote work when any input is invalid. Runtime failures do not stop
independent cells: the report is completed before the command returns failure.

Use `-Mode smoke -SmokeSeconds 10` before freezing the candidate. Each cell
installs the same artifacts, opens the complete 64/256 Connection sets, requires
all 16/64 active streams and every retained canary to move, waits for further
useful progress, and verifies bounded process cleanup. Smoke evidence is
explicitly non-accepting and cannot be passed to the NET-14V verifier. Use
`-Mode acceptance` only after the whole smoke matrix passes; it executes all
eight ten-minute cells, four NET-14V pair verifications and the independent
NET-32 observation while retaining every failure.

The matrix file contains no secrets. Every `Inputs` value names one prepared
`run-inputs.json` outside the repository; all entries must bind the same clean
`SourceCommit`:

```json
{
  "Schema": "ardents-qualification-matrix-v1",
  "SourceCommit": "40 lowercase hex characters",
  "Cells": [
    {
      "Carrier": "tcp-tls",
      "Cell": "net14ad",
      "Profile": "client-to-publisher",
      "Inputs": "C:\\private\\issue60\\tcp-normal-up\\run-inputs.json"
    }
  ],
  "Net32Inputs": "C:\\private\\issue60\\tcp-normal-up\\run-inputs.json"
}
```

`Cells` must contain each combination of `tcp-tls`/`quic`, `net14ad`/
`net14-recovery`, and `client-to-publisher`/`publisher-to-client` exactly once.
The command validates all referenced manifests and plans before starting the
first cell.
