# Actual installed startup

This checked profile runs a root fixture driver outside the Endpoint unit.
The real canonical participant becomes its non-root MainPID through genuine
initial provision and signed retained-Root successor commands. Actual
Installation process/manager/file observations and its own completion exchange
precede qualified Execution permission preparation, genuine TLS Source refresh
and Stock import. Explicit provider input initializes the shared Hosting budget
through the real installed command after Root completion and before Permission
handoff; runtime does not create or reset it. An original-invocation public
bootstrap diagnostic and AAI3 listener
peer PID/UID/GID are observed. The listener probe submits no Service request;
the original process and kernel scope must join before fixture cleanup.

Build cmd/ardents-next and cmd/ardents-text with CGO_ENABLED=0,
-trimpath -buildvcs=false -ldflags=-w, and compile the command test binary with
-tags=text_worker_installed and the same flags. Outside the repository, supply
the participant, Text program and seven maintained packaging resources in one
root-owned immutable directory. Its independently delivered inventory.json
contains nine files entries with name and sha256. The participant name is
ardents-linux-amd64; the Text name is ardents-text-linux-amd64.

Set ARDENTS_EXECUTION_START_TEST, its independent _SHA256,
ARDENTS_EXECUTION_START_RESOURCES, ARDENTS_EXECUTION_START_INVENTORY_SHA256,
ARDENTS_EXECUTION_START_ROOT and ARDENTS_EXECUTION_START_LOG, then run
make execution-installed-check from a fresh isolated Ubuntu24.04/systemd255
manager. An isolated stand must enter its own cgroup namespace and pivot to its
own root filesystem before starting the manager; its outside driver must also
enter that cgroup namespace. The checked preflight requires the original manager
at `/init.scope`; an outer unit prefix refuses before the four-minute test rather
than becoming a product failure. A chroot whose child protection namespace
exposes host-root prefixes
through proc cannot attest the required original executable path. The test's
temporary root and every artifact/log stay outside Git.
Missing privileges, pins, platform or freshness are invalid environments.
Failure retains the new receipt and native Installation residue; restarting
against an existing setup is not first-provision evidence.

The separate `execution-installed-publication-check` target selects
`TestInstalledServicePublication`. Set `ARDENTS_EXECUTION_START_CARRIER` to
`ardents-carrier-tcp-tls-v2` or `ardents-carrier-quic-v2`; run each in a separate
fresh manager with the same independent artifact checks and four-minute bound.
The actual installed dual-role program prepares both approved holder requests.
Fixture Allocation approves requested maxima `[32,32,0]` for Reader and
`[32,32,8]` for Publisher; these are explicit test allocations, not product
defaults. Instance initialization and public Credential acceptance use actual
installed commands; fixture signing supplies no private Instance key or worker.
Publication obtains actual blind tokens through network issuers, then runs the
qualified snapshot worker, real registrations and receiving Descriptor Store.
The scenario checks no Link before publication, a canonical accepting Link,
withdrawal and original process survival without an accepting Link afterwards.
Snapshot uses the declared 45-second total publication bound, with input still
limited to fifteen seconds; Link and withdrawal retain fifteen seconds each.
The driver requires
the exact selected Carrier subcase and rejects every skip. This one-Publisher
component does not establish a Reader Service stream or two installed Endpoints.

The `execution-installed-pair-check` profile runs a separate outer root controller
with `ARDENTS_EXECUTION_PAIR_MANAGERS` naming exactly two original manager PIDs.
Each fresh manager has its own PID, mount and cgroup namespaces and pivoted root,
with the canonical participant profile at `/root/run-profile.sh`, pinned test at
`/root/startup.test`, pinned inventory/resources at `/root/artifacts` and the
trusted root-owned mode-0755 parent `/var/lib/profile-root`. Fixture loopback is
shared. The outer controller uses the same artifact variables as above, a fresh
root/log and an eight-minute harness bound; each participant retains its original
four-minute harness bound. Product deadlines are unchanged.

The controller retains original manager proc directories and passes opened
namespace/root descriptors to `nsenter`. Both guests start before the controller
awaits either admission, with independent serial permission approvals and
unchanged participant deadlines. Each guest independently provisions and
admits its real program, verifies public signed Network input in its own State,
uses its own Source credentials and obtains separately approved permissions.
Service fixtures explicitly declare a sixty-second automatic Source interval;
the separate startup fixture retains its one-second interval. Initial Source
bootstrap still performs a genuine wave. Interruption of an already active wave
retains consumed attempts and durable backoff and can refuse the new startup;
this successful Service scenario does not bypass or qualify that refusal path.
The controller keeps Route/issuer/receiving Store fixtures alive across both
guests. Only public signed material and actual permission requests/responses cross
the local fixture channel; no private Instance or accepting owner is transferred.
The scenario performs Snapshot and Link on Publisher, one exact text exchange
through Reader's actual AAI3 listener, then Withdraw and Link refusal. Both original
participants must join through their registered cleanup. The scenario then
attempts a real unit start without a new Root completion exchange: Startup must
refuse, and retained regular-file paths and bytes must remain unchanged. This
does not demonstrate power-loss consistency or the complete
interruption matrix. The outside stand owner
must retain and stop both original managers after the run. Use a fresh pair for
each Carrier. A passing run alone does not establish full restart/interruption
acceptance.

Service scenarios also require a root x86-64 kernel ptrace observer outside the
Endpoint unit. The pinned test binary's child observes the original replacement
Root's full 160-byte ACK, successful guard-removal record and journal sync, then
kills that original Root at guard unlink entry. Its actual SIGKILL and original
thread/process join remain asserted failures of that command. The same fixture
lifetime keeps genuine Source, clock and signed Candidate inputs alive for a
new public `recover-installed` evaluation. Recovery must remove only the original
guard, preserve all other regular-file bytes/inodes/access/timestamps and Release
floors, and retain the same running PID, InvocationID and original kernel scope.
The ensuing Publication/Reader commands exercise that recovered invocation.
Missing ptrace custody or an unobserved cut fails; no successful observation is
injected. Original product and four/eight-minute harness bounds remain unchanged.
This process interruption does not qualify power loss or other journal phases.

All signing, Source servers and clock observations are fixture-controlled.
The separate `execution-installed-timing-check` selects
`TestInstalledServiceTiming` and `TestInstalledServiceTimingParticipant`, with

[Publication timing profile](../publication-timing/README.md). The ordinary

minutes must remain in the token hour; an unsuitable hour is invalid environment.
Use a fresh pair for each Carrier and retain original outer managers for the
whole profile (at least `RuntimeMaxSec=920s`, `TimeoutStopSec=30s`).

This profile includes the same genuine Installation cut/recovery, first Text
request and independent original invocations. It then waits for the actual
automatic scheduler without a Refresh command or clock adjustment. Independent
Store lookup and proof verification must observe exactly the next revision,
same Publication and different slot/recipient key, followed by a second actual
Reader Text request through the same installed processes. The Snapshot request
provides a real lower bound on registration creation; replacement before +299s
refuses, accounting only for canonical whole-second rounding. Withdrawal,
original cleanup and restart refusal still complete. This is installed refresh
and post-refresh Service evidence; the separate Publication timing profile
retains exact ACK-delay and sixty-second overlap timing obligations.

No independent release custody/builders, Source families, trusted-time service,
private Publication/Connection readiness, complete interruption matrix or
whole-host/privacy qualification follows from this bounded scenario.
