# Enrollment — проект домена

Самостоятельный владелец внутри семейства Software acceptance. Реализация
проверки и read-only consumer находятся в рабочем дереве; готовность и приёмка
подтверждаются отдельно исходниками и доказательствами в выбранной задаче.

**Вопрос домена:** какой первоначальный комплект закреплён независимым доверием?

**Входит:** первичное закрепление manifest и проверка точного состава комплекта,
согласованности поколения и обязательных companions.

**Не входит:** подпись, установка, запуск, Release-разрешение и членство Network.
Самосогласованный непривязанный inventory не является первичным доверием.

**Состояние и завершение:** сохраняет происхождение первоначального pin;
выдаёт проверенный состав либо отказ без частичного доверенного результата.
Не создаёт общий корень с Release или Installation.

**Соседи:** Release отдельно проверяет программную авторизацию; Installation
потребляет точный проверенный комплект и разрешение, сохраняя свою транзакцию.

**Где искать обязанности:** `internal/enrollment` и адаптеры загрузки комплекта.
Текущий код — источник для анализа, не разрешённый импорт.

**Основа:** [Release и Custody](../../../docs/technical/release-update-custody.md),
[карта доменов](../../../docs/development/domain-map.md).

## Контракт до реализации

Технический владелец —
[Enrollment verification](../../../docs/technical/enrollment-verification.md),
а защищённый состав закреплён в
[ADR-0119](../../../docs/adr/0119-bind-protected-endpoint-generation-to-release.md).
Этот проект уточняет организацию нового владельца в пределах этих контрактов.
Он не свидетельствует о принятой реализации. Исполнение и приёмка ведутся в
[задаче Enrollment](https://github.com/dianabuilds/ardents-network/issues/504).

Enrollment отвечает на один вопрос: совпадает ли первоначальный комплект с
независимо полученным manifest pin и обязательным составом? Pin поступает
отдельно от комплекта; найденный рядом с файлами digest не становится доверием.
Уже доверенный consumer проверяет комплект. Самопроверка запущенной программы
не может доказать безопасность её первого исполнения: независимая проверка до
первого запуска остаётся обязанностью Distribution Profile.

| Владелец | Решение | Что получает следующий владелец |
|---|---|---|
| Enrollment | Первоначальный pin, точный состав, байты и согласованность companions | Замороженные проверенные факты и копии байтов с происхождением |
| Release | Подписи, допустимый target, время, версия и неубывающие floors | Собственное непрозрачное разрешение на точные байты |
| Installation | Совместное потребление разрешений программы и поколения, установка и восстановление | Привязку к реально установленным ресурсам |
| Execution | Исходный квалифицированный запуск и локальное право операции | Ограниченное право конкретной живой операции |

Enrollment не импортирует Release, Installation, Execution или старых runtime
владельцев. Преобразование проверенных файлов в запрос реального Release
принадлежит composition с новым Release. Имена и байты существующего формата
сохраняются; историческое имя companion не даёт ему runtime полномочий.

`Bundle.MetadataNames` проецирует отсортированные имена metadata из private
inventory, исключая trusted root и static companions через их существующие
grammar identities. Настоящий `ardents-next` Release consumer использует эту
проекцию вместо собственного списка исключений; URL и Release inputs по-прежнему
принадлежат composition. Проекция не проверяет подписи и не удаляет исходные
companion bytes. General, headless Linux/Windows и protected inventory имеют
независимые portable проверки, включая копирование возвращённых имён.

Для [нового Installation](../installation/README.md) требуется отдельный
successor candidate snapshot без primary pin provenance. `ReadCandidate`
загружает distinct opaque `Candidate`: самосогласованные declarations и копии
байтов, без independent pin и утверждения running-program identity. Его
наблюдаемый manifest checksum не является доверием; `Candidate` нельзя
преобразовать в `Bundle`. Bounded physical reads, inventory, final identity и
cancellation принадлежат той же private Implementation, а классификация
metadata/static files едина для обоих результатов. Подключение candidate к
реальной свежей паре Release-разрешений принадлежит новому Installation и
использует его настоящий command consumer. Проверка пары требует сохранённую
полную историю Release; эти механизмы сами по себе не дают installed successor
authority или права перехода поколения.

## Этапы и точки отказа

1. **Вход.** Проверить независимый SHA-256 pin, Bundle Root, исходный context
   и закрытый выбор general/headless. Consumer получает фактический путь
   собственной программы через ОС; пользовательский флаг не заменяет эту
   идентичность. Не открывать сетевые, Release или устанавливаемые корни.
2. **Manifest.** Ограниченно прочитать обычный файл `SHA256SUMS`, проверить
   физическую идентичность и native ownership. Сравнить pin до разбора содержимого.
   При несовпадении не интерпретировать `RELEASE` и не выдавать доверенные факты.
3. **Состав.** Разобрать канонический отсортированный manifest: не более 32
   записей, прямые имена, обязательный `RELEASE`, без повторов и неизвестных
   записей. Фактический каталог перечислять после аутентификации и разбора
   `RELEASE`, чтобы typed refusal retired version предшествовал работе с
   companions. Ограничить перечисление допустимым числом плюс одной записью
   для обнаружения переполнения, без предварительного чтения всего каталога.
4. **Байты.** Проверить digest `RELEASE` до разбора единственной grammar v3.
   Ограниченно прочитать каждую запись, проверить её digest и оставить именно
   эти проверенные байты. Зафиксировать идентичность открытого файла и повторно
   проверить её после чтения; отказать при обнаруженной замене, изменении,
   symlink, nonregular или превышении лимита. Размер из предварительного Stat
   не является ограничителем чтения. Сохранить лимит 64 MiB на запись;
   учёт памяти включает весь удерживаемый комплект, а не только один файл.
5. **Связность.** Проверить точную привязку текущей программы и парность
   Node/Custody. В headless пара обязательна; частичная пара запрещена в обоих
   вариантах. Protected group либо отсутствует в general/headless, либо полон:
   канонический пяти-полевой descriptor до 16 KiB, ровно девять ресурсов,
   соответствующие program/platform/release/digests. Отсутствие группы никогда
   не означает protected readiness. Linux platform в descriptor — проверяемый
   факт формата, а не причина ограничивать парсер Linux build tag.
6. **Выдача.** Передать целый результат только после завершения чтений,
   повторных проверок и финальной проверки исходного context. Закрыть все
   файловые handles; ошибки чтения и закрытия сохранить. Не возвращать
   частичный доверенный результат или успех после наблюдаемой отмены.

Результат хранит private snapshot, который создаёт только успешный verifier.
Нулевое значение не является проверенным комплектом. Наружу выдаются значения
и защитные копии; mutable map/slice или публичный флаг `Verified` не служат
доказательством. Позднее изменение исходных файлов не меняет snapshot и не
разрешает незаметно перечитать другие байты. Этот результат удостоверяет только
проверенный первоначальный комплект; будущий consumer отдельно проверяет свои
условия актуальности и полномочия.

## Организация кода и ошибки

Первый Module — один cohesive Go package с малым Interface проверки и чтения
замороженного результата. Этапы принадлежат private Implementation. Отдельные
файлы описывают реальные обязанности: проверка комплекта, manifest/inventory,
descriptor, protected generation и физическое чтение. Не создавать вложенные
пакеты ради визуальной группировки или по файлу на каждый короткий метод.

Общие правила и их тесты переносимы. Native Adapter требуется лишь там, где
отличаются ownership, link count или физическое открытие файлов. Unix-проверка
owner-only single-link файла имеет реальное обоснование. Текущий Windows
predecessor не проверяет Unix ownership; новый consumer должен честно сохранять
объявленный уровень гарантии, а не выдавать отсутствие проверки за Ubuntu
qualification. Поведение на других ОС определяется доступным механизмом и
контрактом отказа, не суффиксом всех файлов `_linux.go`.

Ошибки классифицируют неверный вход, несовпадение pin, retired descriptor,
нарушение формата/состава/привязки, физическую недоступность и отмену. Отмена
сохраняет стандартную identity context error; причинная I/O ошибка остаётся
доступной для диагностики. Consumer выводит конечный класс без содержимого
комплекта. Точный Go Interface определяется вместе с реальным consumer;
не добавлять заранее интерфейсы будущих Installation/Execution.

## Проверяемая приёмка

Тесты пересекают тот же Interface, что consumer, с независимо собранными
manifest/descriptor и реальными временными файлами. Положительный сценарий
проверяет полный snapshot и оригинальную привязку программы. Отрицательные
сценарии причинно нарушают конкретный этап: pin до parse, retired/unknown
version, canonical bytes, состав, digest, пары, protected generation, identity,
отмена и изменение файла во время чтения. Проверка без критического guard
должна воспроизвести соответствующий отказ теста. Копии результата отдельно
проверяются на alias mutation.

Реальный read-only `ardents-next` consumer и compiled positive/refusal сценарии
на Windows/Linux входят в ту же поставку. Он не запускает комплект и не создаёт
успешный Release/Execution/Publication substitute. Новый owner включается в
зарегистрированный регресс новых доменов, race/static/isolation и обязательные
repository gates. Приёмка относится к точному исходнику и genuine consumer;
полная цель Route остаётся отдельной и не закрывается этим результатом.
